# Architecture

> **Built so far:** Milestone 1, and Milestone 2's parts, tested locally: a web client with a thread list, a control plane that creates each thread and its sandbox, sandbox providers for Docker, Daytona and local development, a sandbox image in which the agent runs as its own user, thread history in Postgres, and acknowledged delivery between supervisor and control plane that survives either being killed. From Milestone 3: sign-in with Supabase Auth, verified by the control plane, and every thread belonging to one user; and the thread lifecycle: several threads at once, stopping, resuming and deleting them, waking a stopped one with a message, stopping idle sandboxes, a limit on how many run, and reconciling the control plane's records with the provider; and working with a Git repository: cloning it before the agent starts, linking users' GitHub accounts, and publishing a thread's branch or a pull request from the control plane. From Milestone 4, its API-key half: each user's own model keys, stored encrypted, a model per thread, and each thread's agent running on its owner's key alone. From Milestone 5: the live desktop, embedded in the thread page and protected like the thread, which the user watches and can take control of, and a computer tool for the agent. From Milestone 7: the sandbox boundary hardened (the supervisor's token handed over as a file only its user can read, a helper that can make the supervisor's user the agent and no one else), sandbox failures reported with what to do, the model proxy, which keeps the keys of the providers it relays out of sandboxes, and each user's model usage, counted and capped. **Not built yet:** any deployment, and connecting a ChatGPT subscription. Daytona, Supabase and a real GitHub App have never been run against. Sections that describe intended design say so. Update this document as code lands, so that it always matches what the code does.

## The four parts

| Part             | What it does                                                                               | Built today                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| Clients          | Thread list, conversation view, live desktop view                                          | One web page ([`apps/web`](../apps/web)) with the list, the conversation and the live desktop                 |
| Control plane    | Authenticates users, creates and stops sandboxes, relays messages both ways, keeps history | [`apps/control-plane`](../apps/control-plane): signs users in, creates threads and sandboxes, relays, records |
| Data store       | Users, threads, and the ordered record of everything each agent did                        | Postgres (users, threads and their events), or memory for development                                         |
| Thread sandboxes | One isolated Linux computer per thread: the agent, its workspace, a graphical desktop      | A container from [`sandbox-image`](../sandbox-image), through a provider, with a desktop and Firefox          |

Clients are thin: all state lives on the server. The control plane never sleeps; sandboxes run only while there is work, and stop when idle (see [the sandbox's lifecycle](#a-threads-sandbox-lifecycle)).

## Two core design ideas

**The sandbox connects outward.** A small supervisor process inside each sandbox ([`apps/sandbox-supervisor`](../apps/sandbox-supervisor)) starts the agent and opens a WebSocket back to the control plane. The control plane never reaches into a sandbox, so a sandbox needs no inbound networking, and any provider, rented server or laptop can host one the same way.

**Every event is recorded in order before it is shown.** The control plane stores each event with its position in the thread's sequence and only then forwards it. A client that reconnects says where it left off and receives everything it missed: full history, several devices at once, and closing a laptop to pick the thread up on a phone.

## Signing in, and who sees what

A user signs in with **Supabase Auth**, by a six-digit code sent by email, in the web client through supabase-js. The client learns where to sign in from the control plane (`GET /api/client-configuration`, the one API route that needs no token), so one build of the client serves any installation. Supabase hands the client an access token, a JWT that supabase-js refreshes before it expires.

The **control plane verifies every token itself** ([`authentication/`](../apps/control-plane/src/authentication)): its signature against the project's published public keys (fetched and cached with jose, and fetched again for a key it has not seen, which is how a rotated key is picked up), the issuer, the audience `authenticated`, an asymmetric algorithm, the expiry with 30 seconds' tolerance, `role: authenticated` and not anonymous. The user is the token's `sub`. An installation admits only the email addresses it lists (`BARRACK_ALLOWED_USER_EMAILS`), confirmed by asking Supabase, unless it says `anyone-who-can-sign-in`. A user is recorded on their first authenticated request, and every thread records its owner.

**A user sees and controls only their own threads**, and another user's thread is answered exactly as one that does not exist. This is enforced once per transport:

- **HTTP:** a middleware on all of `/api/*`, mounted before any route, requires `Authorization: Bearer <access token>` except on the listed public paths ([`http/require-signed-in-user.ts`](../apps/control-plane/src/http/require-signed-in-user.ts)). Routes learn the user only from it, and the thread store has no way to list or find a thread for a user without the owner's identifier. A test requests every registered route without a token.
- **Client WebSocket:** browsers cannot put headers on a WebSocket, and a URL ends up in logs, so the token is the **first message**. After the upgrade (whose `Origin`, when sent, must be allowed) the connection's session ([`websocket/client-session.ts`](../apps/control-plane/src/websocket/client-session.ts)) accepts only an `authenticate` message within 5 seconds (closing with `authenticationTimedOut` otherwise, which the client retries; it obtains its token before opening the socket), verifies it, checks that the user owns the thread, and only then attaches the client to the thread's relay, which demands a `ThreadAccess` that only that check can produce. The client sends each refreshed token on the open connection, which must name the same user; when the newest expires without a replacement, the connection closes with `accessTokenExpired`, and the client refreshes and reconnects from its last seen sequence.

The supervisor endpoint is unchanged: a sandbox proves itself with its thread's token, not a user's.

For local work, an explicit **development mode** (`BARRACK_AUTHENTICATION=development-single-user`, which `pnpm dev` sets) has one fixed user whose token the control plane hands to any client. It is refused unless the control plane listens on a loopback address, and then answers only requests and upgrades whose `Host` is a loopback name or address, so a web page that rebinds its own domain to 127.0.0.1 is refused; with Supabase it may listen anywhere, under any name.

## Creating a thread

1. The thread list's **New thread** sends `POST /api/threads` with the user's access token ([`http/threads-routes.ts`](../apps/control-plane/src/http/threads-routes.ts)).
2. The control plane mints a thread identifier and a **supervisor token for that thread alone** (32 random bytes), records the thread with its owner, the token's SHA-256 digest and its sandbox `creating`, if the user is under the limit on running sandboxes, and answers at once ([`sandbox-lifecycle/sandbox-lifecycle.ts`](../apps/control-plane/src/sandbox-lifecycle/sandbox-lifecycle.ts)). The token itself is never stored, logged or returned.
3. In the background it asks the configured provider to create the sandbox ([`sandbox-lifecycle/sandbox-creation.ts`](../apps/control-plane/src/sandbox-lifecycle/sandbox-creation.ts)), handing over the supervisor's plain settings, its environment (the control plane's URL, the thread, and which agent runs), and its one secret, the token, which the provider hands the supervisor's user alone as a file, never in the sandbox's environment (see [sandbox providers](#sandbox-providers)). No model and no model key: those reach the supervisor over its connection (see [each user's own model access](#each-users-own-model-access)). The sandbox is then recorded `running` with its identifier, or `failed` with a reason the page shows. A creation cut short by a control plane dying is finished by another (see below).
4. The sandbox's supervisor connects to `/threads/{threadId}/supervisor` with `Authorization: Bearer <token>`. The upgrade is accepted only if the token's digest matches one recorded for that thread (the token minted with it, or one minted when its creation was taken over), compared in constant time ([`websocket/supervisor-authorization.ts`](../apps/control-plane/src/websocket/supervisor-authorization.ts)), so one sandbox cannot act as another thread's supervisor.

## A thread's sandbox lifecycle

The control plane, not the provider, decides when a thread's sandbox runs ([`sandbox-lifecycle/`](../apps/control-plane/src/sandbox-lifecycle)). Each thread records what its sandbox should be and is in, in the `threads` table:

| State      | What it means                                     | Becomes                                                                                                          |
| ---------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `creating` | the provider is making it (lease held)            | `running`; `failed` if the provider refuses                                                                      |
| `running`  | it runs; `problem` says why a stop did not happen | `stopping` (stop, idle); `deleting`; `stopped` or `failed` if the provider stopped or lost it                    |
| `stopping` | the provider is stopping it (lease held)          | `stopped`, or `starting` if a message asked it to wake; after a failed stop, what the provider reports           |
| `stopped`  | stopped, files kept                               | `starting` (resume, or a message; both under the limit); `deleting`; `running` or `failed` if found so           |
| `starting` | the provider is starting it (lease held)          | `running`; after a failed start, what the provider reports                                                       |
| `failed`   | `reason` says why; resumable if it has a sandbox  | `starting` (resume, under the limit); `deleting`; `running` if found running; `failed` without a sandbox if lost |
| `deleting` | being destroyed (lease held)                      | removed with its history; after a failed destroy, what the provider reports                                      |

The legal changes are listed once, in [`threads/thread-store.ts`](../apps/control-plane/src/threads/thread-store.ts), and the store refuses any other. Every change is a **compare-and-set on the thread's version**: whoever decides a change names the version it read, and the update succeeds only if the thread is still at it, moving it on. Two requests, or two control plane instances during a redeploy's overlap, acting on the same reading therefore never both succeed. `creating`, `starting`, `stopping` and `deleting` mean a provider operation is under way, and carry a **lease** that the control plane doing it renews every quarter of its length (two `BARRACK_SANDBOX_CHECK_SECONDS`), and checks once more when the provider call returns. An operation that finds its lease taken gives up where it is: it calls the provider no more, records nothing, removes no history, and destroys a sandbox it made only if the thread is gone or settled without naming it, never one the control plane that took over may adopt. Changes that take a place under the running-sandbox limit count the places taken (a sandbox creating, running, starting or stopping, or being deleted while the thread still has one) and make the change in one transaction holding a lock all such transactions take, so two at once cannot both squeeze in.

- **Stop**, by the user or by idle shutdown: the relay asks the agent to end its run and hands it no more messages; the operation waits up to 5 s for the run to end as the agent reports it, stops the sandbox with its files kept, records the end of any run still open (as cut short), and records `stopped`, or `starting` if a message asked for the sandbox to wake meanwhile. A stop that reports failing although the provider then reports the sandbox stopped is finished the same way, so such a message still wakes it.
- **Resume**: `starting`, then the provider starts the sandbox, and `running`. The supervisor starts afresh, says hello as a new instance, and is handed the messages it lacks; Pi reopens its session file by the thread's identifier, so the model is sent the earlier turns ([`docker-thread-lifecycle.test.ts`](../tests/end-to-end/src/docker-thread-lifecycle.test.ts) shows it).
- **Waking**: before a user message is recorded, the relay asks the lifecycle to admit it ([`thread-relay/thread-activity.ts`](../apps/control-plane/src/thread-relay/thread-activity.ts)). A stopped sandbox is moved to `starting` (if there is a place; otherwise the message is refused with the limit's explanation, naming the user's sandboxes to stop, and not recorded; the page keeps it, offering to send it again), a stopping one is asked to wake once stopped, and the message waits in history until the supervisor attaches. A message is never recorded to wait for a stopped sandbox nothing is waking: if the thread keeps changing under the wake, it is refused too. One left waiting all the same (its sandbox failed to start, say) is shown with what to do: resume the thread.
- **Idle shutdown**: every check, running sandboxes with no activity for the idle period are candidates; one whose agent has a run open, or a message waiting to be delivered, is left. The stop is made only if the thread's last activity is still the one read, so a message arriving in between keeps it running. Activity is a user message (noted before it is recorded), a supervisor's event, the agent's or the clone's (noted before it is recorded, at most once a minute or a quarter of the idle period per thread), or a publication under way (noted at its start and every 30 seconds); a client watching is not. A clone that outlasts the idle period with no message waiting can therefore be stopped; it is cloned again from the start when the sandbox wakes, since only a finished clone is recorded.
- **Delete**: `deleting`, the sandbox destroyed, then the history and the record removed, and the history removed once more through the thread's relay queue, behind a message admitted just before the deletion that may still be on its way into the log (one queued after it finds no thread and is refused). A message admitted by another control plane instance during a redeploy's overlap is not behind that queue, and can still leave its rows.
- **Reconciliation**, at startup and every check: an operation whose lease has expired is taken over (a compare-and-set again, so only one instance does) and carried on from its provider step, every provider operation being safe to repeat. A creation taken over mints a new token and adds its digest to those the thread accepts before asking the provider; a sandbox that turns up already made (by an earlier attempt, or by a request of this one that seemed to fail) is adopted and started, which launches its supervisor if it is not running, and its token, whichever attempt minted it, is still accepted. Then each running sandbox (at startup, each stopped and failed one too) is compared with the provider's `getStatus`: one stopped, failed or lost by the provider is recorded so, with any run it left open closed; one recorded stopped that runs is recorded running.
- **Failures**: a provider operation that fails leaves the state the provider then reports, with a reason for the user; only if even that cannot be read is the sandbox recorded `failed` (resumable). A provider reports a failed sandbox with a `cause` and a reason in words a user can read (the supervisor's own last words where it can read them: Docker's provider reads the end of the container's standard error, where the supervisor writes why it stopped), and the reconciler turns each cause into what to do: a supervisor that refused to start (exit code 78) will fail the same way until the installation is fixed; one that crashed, ran out of memory or found a disk full can be resumed. A creation refused because the sandbox image cannot be found says the administrator must provide it. A running sandbox found stopped says something other than Barrack stopped it.
- **A supervisor that never connects**: each thread records since when its sandbox has awaited its supervisor (`awaiting_supervisor_since`, migration 0110): set when the sandbox is asked to be created or started, set again when it is recorded running if none has attached meanwhile, and cleared when one is welcomed. A running sandbox that has awaited its supervisor for five minutes is moved to `stopping`, stopped, and its thread recorded `failed` (resumable), naming the address sandboxes were given (`BARRACK_SANDBOX_CONTROL_PLANE_URL`) as the likely cause; without this, a sandbox that can never reach the control plane would run, and be billed, for ever, and its thread show as starting with no clue why.

What the lifecycle needs of history it reads without reading events: the event log's counter row per thread holds whether a run is open and the sequence of the newest user message, beside how far messages have been delivered, so the thread list and idle shutdown cost one indexed read per thread, or one query for a whole page.

## Working with a Git repository

A thread may start from one repository ([`repositories/`](../apps/control-plane/src/repositories), [`github/`](../apps/control-plane/src/github), [`publication/`](../apps/control-plane/src/publication) in the control plane; [`workspace/`](../apps/sandbox-supervisor/src/workspace) in the supervisor). The rule throughout: **the sandbox never holds a credential that can write.**

**Choosing it.** `POST /api/threads` may carry `{ repository: { url, access, baseBranch? } }`. URLs must be `https://`, with no credentials, query, fragment, percent-encoding or `..` (`repository-url.ts`); plain `http://` only with `BARRACK_ALLOW_PLAIN_HTTP_REPOSITORIES=development-only`, for tests. `access` is `none` (a public repository, cloned with no credential, from which nothing can be published) or `github_app` (one of the user's repositories, through the installation's GitHub App). For `github_app` the repository must be among those the user was verified for when they linked GitHub, and is checked with GitHub again (`live-repository-access.ts`): the App's installation must still include it and the user must still be able to push. A base branch, the one asked for or GitHub's default, must be a name `git check-ref-format --branch` accepts (`branchNameSchema`, which also refuses control characters beyond ASCII); a default branch that is not is refused, naming it. The repository is recorded with the thread, in the same transaction (`thread_repositories`, migration 0040), with its work branch, `barrack/<thread id>`.

**Linking GitHub** (`github-connections.ts`). Settings' **Connect GitHub** asks the control plane to start: it records the SHA-256 of a random `state`, the user and a PKCE verifier for ten minutes, and sends the browser to GitHub's authorisation page. GitHub sends the browser back to the web client's `/github/callback`, which hands the code and state to `POST /api/github/connection` **with the user's own access token**; the state must exist, be unused, unexpired and that user's, and is consumed either way. The control plane exchanges the code (with the verifier) for a user token, asks GitHub with it who the user is, which of the App's installations they can reach and, in each, which repositories they can push to, stores that list, and revokes the token. No GitHub token is ever stored, and no `installation_id` from a redirect is ever trusted.

**Cloning** (`thread-workspace.ts`). Right after `supervisor_welcome`, before any user message, the relay sends `prepare_workspace`: the repository, the work branch, and the commit author (the user's GitHub no-reply address if they linked GitHub, otherwise a placeholder at a domain that receives no mail). The supervisor clones, **as the agent**, a partial clone (`--filter=blob:none`, so the whole history but contents only as they are needed) into the workspace, switches to the work branch, and records the clone in its own state directory. It reports `repository_clone_started`, then `repository_cloned` (base branch and commit) or `repository_clone_failed`, numbered and acknowledged like agent events. Until the clone succeeds the agent is given no message; each message retries the clone first, and is acknowledged without reaching the agent if it fails again. Nor is a message given before `prepare_workspace` has arrived and been acted on: one that comes first is withheld the same way, with a `repository_clone_failed` saying the workspace was never described. A stopped and resumed sandbox finds its record and does not clone again; a sandbox made afresh after the agent had worked clones again and says the earlier work was lost.

**Credentials for reading.** For `github_app`, the clone is configured with a credential helper (`git-credential-helper.ts`) that Git runs as the agent. It asks the supervisor on a Unix socket only the sandbox's users can reach, which answers only questions about the thread's repository, and asks the control plane with `repository_credential_request`. The control plane (`repository-credentials.ts`) decides the repository from the connection's thread, never the request, checks the owner's link still includes it, and answers with a GitHub App installation token restricted to that one repository and to `contents: read`, reused while it has more than fifteen minutes left. Before minting one it asks GitHub whether the App still reaches the repository and the owner can still read it: if GitHub says no, the token handed out last is revoked and the request refused with the reason, which the agent's Git shows (the thread keeps what it cloned, and publishing is refused too); if GitHub cannot be asked, nothing is minted, but the last token is handed out again while it lasts. Requests are limited to 30 at once and one every two seconds after. The token travels in memory, through the socket, to Git; it is never in a file, URL, argument, log or event.

**Publishing** (`thread-publisher.ts`), from the thread page's **Push branch** and **Open pull request**, is the control plane's alone:

1. It checks with GitHub that the owner may still push, then sends `create_publication_bundle`.
2. The supervisor runs `git bundle create - <base>..refs/heads/barrack/<thread>` as the agent, into a file only it can read, no larger than asked (100 MB), and uploads it with `PUT /threads/{id}/supervisor/publication-bundles/{publication}` and its own token, checked as for its WebSocket. The control plane takes one upload per publication it asked for, streams it to disk counting its size, and cuts it off once the publication stops waiting (a reported failure, or three minutes). The bundle does not travel on the socket: it can be far larger than a frame, and would hold up the thread's events behind it.
3. The control plane treats the bundle as hostile, in a throwaway bare repository (`isolated-git-repository.ts`): it reads the header itself (version 2 or 3, SHA-1, not filtered, exactly one reference, `refs/heads/barrack/<thread>`); fetches the base branch without contents; checks the bundle's prerequisites are there (`git bundle verify`); indexes its pack with every object checked (`index-pack --fsck-objects`, which refuses trees that plant `.git`, hooks or configuration); and only then fetches the one branch. Git runs with no system or user configuration, hooks off, only HTTPS allowed (reading the bundle file is allowed for that one command), and the write token reaching it through a credential helper reading the environment of Git's own process, configured for the remote's exact URL alone (`credential.<url>.helper` with `credential.useHttpPath`), with redirects not followed (`http.followRedirects=false`), so the token is offered to no other server. Every Git command runs under limits (`git-child-limits.ts`, `run-limited-git.ts`): 1 GiB of address space, 120 s of processor time and a 2 GiB file size per process, set with the shell's `ulimit` before it becomes Git and inherited by everything Git starts, and 300 s of wall time and 2 GiB for the publication's whole directory, which the control plane enforces by killing Git's process group. Going over one fails the publication, naming which limit; it never affects the control plane.
4. It pushes to `barrack/<thread>` only, with a write token minted for that one repository, deciding by ancestry (`push-decision.ts`) against the branch as fetched from the repository: a new branch or a fast-forward is pushed; a rewrite only over Barrack's own last push with nothing anyone else pushed beneath it (`replaceable_commit`); anything else, or a question Git cannot answer, is refused. The push carries Git's lease on the commit read, so anyone pushing meanwhile makes it fail rather than be overwritten. A branch found already at the commit is reported published but never recorded as Barrack's own.
5. If asked and none is recorded, it opens a pull request as the App, with a separate `pull_requests: write` token; a later publication updates the same branch and opens no second one. Tokens are revoked after use.

Each outcome is recorded as `repository_published` (commit, branch link, pull request) or `repository_publication_failed`, once per publication: the control plane mints an identifier for each, which names its upload and is the key of its outcome in the event log (migration 0070), so a retried recording, or a second control plane, cannot record one publication twice or as both published and failed. Publishing needs the sandbox running; for a `none` repository, or without a GitHub App, the thread page says why it is unavailable instead. A thread's deletion abandons its publication: the relays tell the publisher when a deletion begins (`listenForEndings`), which stops waiting for the bundle, kills Git, pushes nothing after that, and records nothing; the publisher also reads the thread's record before pushing and before recording, for a deletion made through another control plane. A sandbox that begins stopping fails a publication still waiting for its bundle at once, with the reason recorded; one that already has its bundle finishes without it. A publication under way counts as activity in its thread (noted at once and every 30 seconds), so idle shutdown leaves its sandbox running.

## Each user's own model access

Barrack pays for no model use: each user adds their own API key for each model provider they use, and each thread runs on a model its owner chose, on its owner's key for that model's provider ([`model-access/`](../apps/control-plane/src/model-access) in the control plane; [`pi/pi-credential-file.ts`](../apps/sandbox-supervisor/src/pi/pi-credential-file.ts) and [`pi/classify-model-access-error.ts`](../apps/sandbox-supervisor/src/pi/classify-model-access-error.ts) in the supervisor).

**What can be chosen.** The providers and models offered come from [`@barrack/model-catalogue`](../packages/model-catalogue), a file generated from the pinned Pi itself: every provider Pi can use with an API key, what its key login asks for (the key, and any settings such as Cloudflare's account), and the chat models Pi lists for it. The control plane serves it (`GET /api/model-catalogue`) without installing or running Pi; a test fails when the supervisor pins another Pi, or the installed Pi lists something the file does not, until the file is generated again. A user may still enter any `provider/model` the list lacks, since providers add models faster than Pi is released.

**Where keys live.** In Settings (`PUT`/`DELETE /api/model-credentials/{provider}`) a user adds, replaces and removes one key per provider. The control plane checks that it could be a key (printable, no spaces or quotes, 8 to 8,192 characters) and that the settings are exactly those the provider needs, and calls no provider. It seals the key and its settings with AES-256-GCM under `BARRACK_MODEL_CREDENTIAL_KEY` from its configuration, which the database never holds, with the owner and provider as associated data, so a sealed key moved to another row does not open ([`credential-keyring.ts`](../apps/control-plane/src/model-access/credential-keyring.ts)), and stores it in `model_credentials` (migration 0080), or in memory. No answer, log line or event ever holds a key: clients learn only the provider, when it was added and its last four characters. At startup the control plane refuses to run if any stored key was sealed under a key it was not given, and seals again under the current key whatever a previous one sealed, at startup and every five minutes, skipping what it cannot open. A key sealed under a key this instance does not hold (during a rotation's overlap) is never told to a sandbox as missing: its supervisor keeps the key it has (see the [deployment guide](deployment.md#users-model-keys-and-the-key-that-seals-them)).

**A model per thread.** `POST /api/threads` takes `model`, and `PUT /api/threads/{id}/model` switches it; either is refused (`409 model_credential_missing`, naming the key to add and where) when the user has no key for the model's provider. The model is recorded with the thread (`threads.model`).

**How access reaches the agent.** The control plane sends `configure_model_access` (the model, and what reaches its provider on the owner's account, or none) right after `prepare_workspace` on every welcome, and again when the owner replaces or removes that key or switches the model, and before handing over any user message if it has changed meanwhile (so a key changed through another control plane instance is caught too). It decides both from the thread's record alone; nothing a supervisor sends asks for a credential, so a sandbox only ever receives what reaches its own owner's key for its own model's provider. What that is depends on the provider (its catalogue entry's `keyPlacement`):

- **Key kept on the server** (`kept_on_server`), for the providers the control plane relays (see [the model proxy](#the-model-proxy)): a `proxy_token` credential, a token minted for this supervisor connection and this provider, and the proxy's address for this thread and provider. The owner's key never leaves the control plane.
- **Key placed in the sandbox** (`placed_in_sandbox`), for every other provider: an `api_key` credential, the owner's key itself.

The supervisor remembers the secret only to redact it from everything it reports or logs, and the Pi harness writes it, as the agent's user, to Pi's own credential file (`auth.json` in Pi's agent directory, mode 0600, by an atomic rename), which Pi rereads before each request: a replaced credential is used from the next request, with no restart. For a relayed provider it also sets that provider's `baseUrl` in Pi's `models.json` to the proxy's address, leaving everything else in the file as it is ([`pi/pi-credential-file.ts`](../apps/sandbox-supervisor/src/pi/pi-credential-file.ts)). Neither is in any process's environment: not the container's, not the supervisor's, not Pi's, so nothing started in the sandbox through `docker exec` or a provider's command interface inherits it, and the agent's commands do not print it with `env`. The file is erased at the supervisor's start (a killed supervisor's leftover), when the credential is withdrawn, and when the supervisor stops, so a stopped sandbox keeps nothing. Pi runs only while it has a credential: it is started once the first arrives, stopped when it is withdrawn (after the run in progress), and started again on another model, resuming its session, when the thread switches models, since the pinned Pi offers no provider that had no key when it started. The new model is sent the whole conversation. A switch takes effect for the next run: until the run in progress ends, Pi's file keeps the running model's provider's credential beside the new one's ([`pi/pi-credential-plan.ts`](../apps/sandbox-supervisor/src/pi/pi-credential-plan.ts)), and the proxy still accepts that provider's token while the thread has a run open.

**What the agent can do with it.** The agent runs as the file's owner, so it can read whatever it was given, and so can any code an untrusted repository makes it run. A key placed in the sandbox can be sent anywhere and used for anything the key allows; the user is told so beside every such provider and advised to use a key with a spending limit. A proxy token is worth nothing outside Barrack: it works only at this control plane's proxy, for its own thread and provider, while the thread runs, within its owner's cap, and is revoked when the sandbox stops. Sent elsewhere it can do no more than the agent could already do from inside the sandbox while the thread runs.

**No key, no agent.** A user message to a thread whose owner has no key for its model's provider is refused before it is recorded, with what to add and where, and the page keeps it to send again (as with the sandbox limit); the thread page shows the same. One recorded before the key was removed reaches an agent with no key, which answers it with an errored message saying so (`errorKind: "credential_missing"`). Adding the key sends it to the running sandbox at once, and the next message works; nothing is recreated.

**Failures the user can act on.** When the provider refuses a request, the Pi harness classifies Pi's error report into `credential_rejected` (replace the key), `quota_exhausted` (add credit, or switch model) or `rate_limited` (wait; reported only once Pi's own retries ran out), carried as the errored assistant message's `errorKind` beside the provider's own words; the page explains each and links to Settings where that is the fix. The proxy passes the provider's status and error body through unchanged, so this works the same for relayed providers (shown with the real Pi through the proxy in [`local-model-proxy.test.ts`](../tests/end-to-end/src/local-model-proxy.test.ts)); the proxy's own refusal for a reached cap is classified as `usage_cap_reached`. The run ends as usual, and sending another message, after fixing the cause or switching model, carries on.

## The model proxy

For a relayed provider the agent's requests go to the control plane, at `/threads/{threadId}/model-proxy/{providerId}/…`, which forwards them to the provider with the owner's key and streams the answers back ([`model-proxy/`](../apps/control-plane/src/model-proxy) in the control plane).

**Which providers.** Those listed in [`relayed-providers.ts`](../packages/model-catalogue/src/relayed-providers.ts): Anthropic, OpenAI, OpenRouter, xAI, DeepSeek, Groq, Cerebras and Together, each with the wire formats it is relayed in (Anthropic's Messages API, OpenAI's Responses API, OpenAI's Chat Completions API) and the provider's own address for each. A provider is listed only if every model the pinned Pi offers for it speaks a listed format at a listed address, authenticated by the key alone; a test checks that against Pi itself. Every other provider keeps its key in the sandbox (see the [decision log](decisions.md)).

**Where it sits.** The server hands requests for that path to the proxy before the HTTP app sees them ([`http/route-http-request.ts`](../apps/control-plane/src/http/route-http-request.ts)), so the proxy works on Node's own request and response, streaming both ways with backpressure. It is outside `/api` because the caller is a sandbox proven by its token, not a signed-in user; in development mode the `Host` check applies to it as to everything else.

**Each request, in order** ([`model-proxy.ts`](../apps/control-plane/src/model-proxy/model-proxy.ts)):

1. **The path.** Plain segments only (no percent-encoding, no `.`, `..` or empty segments), a valid thread and provider, and exactly one of the provider's relayed requests: `POST /v1/messages` (with or without `?beta=true`), `POST /responses` or `POST /chat/completions`, as its formats allow. Anything else is refused (404 or 405) before any credential is read.
2. **The limits**, which cost nothing to check: at most 4 requests at once per thread and 256 per instance, and a burst of 20 requests per thread refilled at 2 a second (`429` with `retry-after` for the thread, `503` for the instance, both of which the agent retries).
3. **The records**, read afresh for every request ([`model-proxy-authorization.ts`](../apps/control-plane/src/model-proxy/model-proxy-authorization.ts)): the token (from `x-api-key` or `Authorization: Bearer`) must match, in constant time, a digest minted for this thread and this provider; the thread's sandbox must be recorded running; the provider must be its model's, or the one before a switch while a run is still open; the owner must still be admitted (an installation that lists addresses compares the digest of the owner's last confirmed address, recorded at sign-in, with the list as it is now); the owner must have a key for the provider; and their usage cap must not be reached. The owner and the key come from the thread named in the path, which is the thread the token was minted for, so a token can never spend another user's key. A refusal is written as the provider would write an error, in words the harness classifies.
4. **The request, rebuilt** ([`relay-request.ts`](../apps/control-plane/src/model-proxy/relay-request.ts), [`proxy-headers.ts`](../apps/control-plane/src/model-proxy/proxy-headers.ts)): to the provider's own address and path, by Node's client, which follows no redirect (one answered is refused, `502`); with only `content-type`, `accept`, `anthropic-version`, `anthropic-beta` and the session-affinity identifiers some providers route prompt caching by, `accept-encoding: identity`, and the owner's key as the format expects it. The body is streamed through as it arrives, at most 32 MiB.
5. **The answer, streamed back**: the provider's status, and only `content-type`, `retry-after`, `retry-after-ms`, `x-should-retry` and rate-limit headers, none holding the key; the body decompressed if the provider compressed it anyway, counted (at most 64 MiB), read for usage as it passes, and with any occurrence of the key replaced, even split across chunks. The provider is read only as fast as the agent reads; either side silent for 5 minutes, no first byte within 5 minutes, or an hour in all, ends the request. The agent hanging up cancels the provider's request, and a thread's sandbox beginning to stop ends its requests in flight on this instance.

Only metadata is logged: the thread, provider, owner, statuses, sizes and durations; never a body, a header's value, a token or a key.

**Tokens.** Minted per supervisor connection and provider (32 random bytes), kept as SHA-256 digests in `model_proxy_tokens` (migration 0100), the newest four per thread and provider, so a supervisor that reconnects a few times keeps working. Being in the database, a token minted by one control plane instance is accepted by the other during a redeploy's overlap. A thread's are all removed when its sandbox begins stopping or the thread is deleted (and with the thread's record); a resumed sandbox's supervisor is given new ones. A sandbox whose stop failed is given new ones once the stop is over.

**Through Railway.** Railway ends a plain HTTP response after 15 minutes. A model answer streamed for longer than that through a Railway-hosted proxy is cut off: the agent sees a broken stream and, by its retry rules (which treat a dropped connection as worth retrying; not seen against Railway itself), sends the whole request again; the provider bills what it generated before the cut, and the proxy counts that as an estimate. Answers that long are rare (an agent's turns are seconds to a few minutes); a deployment that needs longer ones needs a host without the cap. Every relayed request and answer crosses the control plane, so its egress grows by the size of each answer; requests are larger than answers, since they carry the conversation, but inbound traffic is not billed on Railway.

## Model usage and its cap

Every answer a thread's model gives is counted, per user, thread, model, how it was counted, and hour, in `model_usage` (migration 0100), one row per hour a thread used a model ([`model-usage/`](../apps/control-plane/src/model-usage)): input, output, cache-read and cache-write tokens, never overlapping, and how many answers.

- **Measured**, for relayed providers: the proxy reads the provider's own figures from the answer as it streams by (Anthropic's `message_start` and cumulative `message_delta`, OpenAI's `response.completed`, a Chat Completions answer's last chunk) ([`usage-meter.ts`](../apps/control-plane/src/model-proxy/usage-meter.ts)). These are trustworthy: the sandbox cannot change them.
- **Estimated**, for a relayed answer cut short before the provider gave its figures (the agent hung up, a limit ended it): the input as the provider gave it, or the request's size in bytes divided by four, and the output from the characters seen generated, divided by four. Otherwise an agent could hang up just before the end of every answer and never be counted.
- **Reported**, for providers whose keys are placed in the sandbox: what Pi says each answer used, carried as the assistant message's `usage` and counted once, as its event is recorded once. The sandbox could say anything, so this is shown, never trusted.

**The cap.** An operator may set `BARRACK_MODEL_USAGE_CAP_TOKENS`, a cap on every user over the last `BARRACK_MODEL_USAGE_CAP_WINDOW_HOURS` (24 by default, counted in whole hours), and a user may set a lower one for themselves in Settings (`PUT /api/model-usage/own-cap`). The cap counts measured and estimated tokens of all four kinds. Once it is reached, the proxy refuses the owner's requests with a non-retried error the harness reports as `usage_cap_reached`, so a running thread's run ends cleanly at its next request rather than asking again, and a new user message to a thread on a relayed provider is refused before it is recorded. Requests already under way finish, so usage can pass the cap by what they use. For providers whose keys are placed in the sandbox the cap cannot be enforced, since the agent reaches the provider itself, and reported usage does not count towards it; Settings says so. Barrack counts tokens and prices nothing.

**Where users see it.** Settings shows the window's count against the cap, the last 30 days by model and how each was counted (`GET /api/model-usage`); a thread's page shows what it has used (`GET /api/threads/{threadId}/model-usage`).

## The live desktop

Every sandbox from Barrack's image has a graphical desktop, which the thread's owner watches in the thread page and can take control of, and which the agent uses through a computer tool ([`desktop/`](../apps/control-plane/src/desktop) and [`websocket/desktop-*.ts`](../apps/control-plane/src/websocket) in the control plane; [`desktop/`](../apps/sandbox-supervisor/src/desktop) and [`pi/computer-use/`](../apps/sandbox-supervisor/src/pi/computer-use) in the supervisor; [`desktop/`](../apps/web/src/desktop) in the web client). The handshake is specified in [`desktop-messages.ts`](../packages/protocol/src/desktop-messages.ts).

**In the sandbox.** `barrack-desktop` runs TigerVNC's Xvnc (an X server and a VNC server in one process, 1280×800, on loopback only, no password, every viewer shared, at most 15 updates a second) and the Openbox window manager, as the agent. The supervisor starts it whenever the sandbox runs and starts it again whenever it ends, and tells the control plane whether there is a desktop (`desktop_availability`). Firefox is installed; the agent starts it when it wants it. A sandbox whose image names no desktop command (the local-process provider's) has none, and says so.

**Reaching a viewer, with nothing reaching into the sandbox.** The page opens `/threads/{threadId}/desktop` and authenticates with its first message, exactly as the thread's connection does (the same token, the same answer for another user's thread as for a missing one, closed when the token expires). The control plane checks that the sandbox runs (a stopped one is not woken; the page offers to), that its supervisor is attached and reports a desktop, and that the thread has fewer than four viewers. It mints a stream identifier and asks the supervisor for that stream (`open_desktop_stream`); the supervisor connects to its VNC server and dials `/threads/{threadId}/desktop-streams/{streamId}` with the thread's token, which the control plane accepts once, only for that thread, within 10 seconds. The control plane sends the page `desktop_ready` and splices the two sockets; the page hands its socket to noVNC in the same moment, so no credential is ever in a URL. Each viewer is its own VNC client of the sandbox's server. The provider's own address for a service (`getServiceAddress`) plays no part.

**Watching and control.** The control plane reads what each viewer sends as VNC messages and passes keyboard, pointer, clipboard and screen-size messages only from the viewer that holds control; it forces shared sessions, keeps only allowed encodings, and closes a viewer that sends anything else. A viewer takes control with `take_desktop_control` on its socket and gives it back with `release_desktop_control`; its connection closing (a hidden tab closes it) gives it back too. Every client of the thread is told which viewer holds control (`desktop_control_status`), and the supervisor whether the user does (`desktop_control`), which it writes to a file the agent's computer tool reads before every input and refuses while the user holds the desktop. That refusal is a courtesy, not a boundary.

**Bounds.** Each direction of a stream stops being read while the other side has more than 1 MiB waiting, until it drains below 256 KiB; the supervisor's side does the same through Node's stream pipeline. A sandbox may send a viewer 4 MiB a second on average, a viewer the sandbox 512 KiB; a viewer that stops reading for 20 s is disconnected. What the sandbox sends is relayed unparsed and drawn on a canvas by noVNC.

**Activity.** Watching does not keep a sandbox awake; the controlling user's input does, noted like the agent's. When the sandbox stops, its streams end (`desktopStreamEnded`), the page says the sandbox is stopped, and the desktop returns when it is woken.

**The computer tool** is a Pi extension the harness loads in a sandbox with a desktop: screenshots read from the local VNC server, input through `xdotool`, coordinates in the screenshot's pixels (the display's own at 1280×800), only the newest three screenshots kept in the model's context. History keeps what it did in words; the images stay in the sandbox.

## Sandbox providers

The control plane sees only the `SandboxProvider` interface ([`packages/sandbox-providers`](../packages/sandbox-providers)): create a thread's sandbox, start, stop, destroy, read its state, and get an address for a service inside it. Providers hold no lifecycle policy; whenever a sandbox runs, its supervisor runs with the environment and secrets it was created with. A creation names the two apart: settings become the sandbox's environment, which every process in it, and anyone who can inspect it, sees; each secret becomes a file in a directory only the supervisor's user can read (`BARRACK_SUPERVISOR_SECRETS_DIRECTORY`), kept across a stop and a start, and never appears in the environment, in what the provider reports, or in a command's arguments, which the contract suite checks of every provider. One is chosen by `BARRACK_SANDBOX_PROVIDER`:

- **docker**: a container per thread from the sandbox image, through the Docker CLI, with every capability dropped but the two the supervisor needs to start the agent. It is created, given its secrets by `docker cp` from standard input, then started. Tested end to end.
- **daytona**: a Daytona sandbox from a snapshot of the image, its secrets uploaded through Daytona's file API. Built and unit-tested against a fake API; never run against Daytona.
- **local-process**: for `pnpm dev` and fast tests. A directory and a supervisor process on the control plane's own machine, with no isolation at all; refused unless development use is declared, and only on a loopback address.
- **fake**: in memory, for the control plane's own tests.

## Inside a sandbox: two users

In the sandbox image, the supervisor runs as `barrack-supervisor` and starts Pi as `barrack-agent` through `run-as-agent`, a small program of Barrack's own ([`run-as-agent.c`](../sandbox-image/run-as-agent.c)) that alone carries the capabilities to change user, only the supervisor's group may run, and can make its caller `barrack-agent` and no one else, with no capabilities and `no_new_privs` set, so nothing the agent runs can gain a privilege. The token is a file only the supervisor's user can read, and then in the supervisor's memory; Linux shows a process's memory, and lets it be signalled or traced, only to its own user, so the agent cannot reach the token through the supervisor's process either. The agent owns its workspace and Pi's state; the supervisor's run, log and state directories are closed to it, so the agent cannot rewrite the supervisor's record of how far it has been handed user messages. What remains open is listed in the [sandbox image's README](../sandbox-image/README.md#what-the-agent-can-still-reach) and the [decision log](decisions.md). Under `pnpm dev` both run as the developer's user, which the local-process provider declares by name (`BARRACK_AGENT_SHARES_SUPERVISOR_USER=development-only`); anywhere else a supervisor without a separate agent user, or running as that user, refuses to start the agent.

## History

Thread events are appended to the thread event log ([`thread-event-log/`](../apps/control-plane/src/thread-event-log)), which assigns each a **sequence**: 1 for a thread's first event, one more for each later one, no gaps. With `BARRACK_DATABASE_URL` set it is Postgres, in a schema of its own, migrated at startup; one statement updates the thread's counter row and inserts the event, so sequences stay gapless even with two writers. Without it, memory.

A client connecting to `/threads/{threadId}/client` names the last sequence it holds. Once it has authenticated and been found to own the thread, the control plane announces the range it missed, replays exactly those events **a page of 100 at a time**, paced by how fast the client reads, then sends whether the supervisor is connected, how far user messages have been delivered, and the text streamed so far of a message in progress, and only then live traffic (the order is specified in [`client-messages.ts`](../packages/protocol/src/client-messages.ts)). A live client is sent each event only if it is the one after the last it was sent: one it already has is skipped, and one further on means it missed an event this control plane never broadcast (another instance recorded it, say), so it is **disconnected to replay rather than shown a gap**. A client claiming more than the log holds is replayed from sequence 1.

## Acknowledged delivery

Between a supervisor and the control plane nothing durable is lost to a dying connection, half-open or not, or to either side being killed; the handshake is specified in [`supervisor-messages.ts`](../packages/protocol/src/supervisor-messages.ts).

- **Each connection starts with a handshake.** The supervisor's `supervisor_hello` names its **instance** (a fresh identifier each time its process starts) and how far the agent has been handed user messages. The control plane answers `supervisor_welcome` with the last of that instance's events it has recorded.
- **Agent events, exactly once and in order.** Each is numbered within its instance and kept in the supervisor's memory until `agent_events_recorded` confirms it durable; everything unconfirmed is sent again after each welcome. The event log stores an event once per instance and number, enforced by a unique index inside the append statement, so a resend or two overlapping control planes never record one twice, and a duplicate leaves no gap. An event whose append failed is sent again when the supervisor reconnects. The control plane refuses an event that skips a number.
- **User messages, exactly once and in order.** A message is recorded whether or not a supervisor is connected, once per identifier its client minted: a unique index on the thread and identifier makes a retry of a message already recorded (its answer lost, or reported unsaved after a database timeout but committed) record nothing, and the relay broadcasts the recorded event instead, so the agent never receives it twice; clients are told how far messages have been delivered (`user_message_delivery_status`) and show the rest as waiting. On every welcome the control plane sends each recorded message after the furthest delivery known, its own record or the supervisor's claim, and then each new one as it is recorded, with its sequence. The supervisor writes the position to its own state directory before handing a message to the agent, ignores anything at or before it, and acknowledges with `user_messages_delivered`.
- **Runs that cannot end are closed.** The event log remembers which instance opened the run still open. A supervisor that reconnects as the same instance finishes its own run, however long it was away; one that attaches as a new instance means the old process, and whatever it had not had confirmed, is gone, so the control plane records `agent_failed` saying so, and clients stop showing the agent working. Every end the control plane records on its own initiative (here, after a stop, and when reconciliation finds a sandbox stopped) goes through one conditional append that names the run by the instance that opened it and records nothing unless that run is still the open one, so two instances, or a stop and reconciliation, never record one run's end twice, and a run opened since is never closed by mistake. Every append has a key that recognises a second attempt: a supervisor event's instance and number (the clone's events included), a user message's identifier, the run a control plane end closes, or the publication whose outcome it records.
- **What can still be lost.** Unconfirmed events are in memory only: if the supervisor process dies, those die with it (normally milliseconds' worth; during a control plane outage, everything since it began). If it dies between noting a message and handing it over, that message is lost rather than repeated. If too many events wait unconfirmed (32 Mi characters), the supervisor exits rather than drop one. Interrupts are sent at most once and never stored. Stream fragments are best-effort.
- **What waits to be recorded is bounded.** Everything a supervisor sends waits in its thread relay's queue behind the append under way, and the sandbox is untrusted. At most the supervisor's own unconfirmed limit plus one frame (36 Mi characters, counted per thread across all its connections) may wait; a supervisor that sends more is disconnected with 1013 (try again later), and resends what was not recorded once it reconnects, so nothing durable is lost. Stream fragments have a budget of their own (1 Mi characters) and are dropped past it, with the rest of that message's fragments, rather than queued. A thread takes at most four supervisor connections at once, since each can hold a frame being received. Each thread has its own queue, so one thread's backlog never delays another's events. Workspace requests (credential requests, a bundle that could not be made) do not wait in the queue, so they are bounded by their own limits instead: credential requests by a per-thread rate, past which they are refused without waiting on anything, with at most one GitHub mint under way per thread and none for a minute after GitHub refused one; and whatever the control plane sends a supervisor, these answers included, by a 16 MiB limit on its send buffer, past which a supervisor that has stopped reading is disconnected with 1013.
- **Everything the supervisor claims is checked**: a delivery position beyond the thread's history, an event number that skips one, an acknowledgement of a message never sent, or anything before the hello closes the connection as invalid.

Every frame must fit the protocol's `maximumFrameLength`, except that a client that has not yet authenticated is dropped once it sends more than the largest `authenticate` message could take (about 97 KiB), so it cannot make the control plane buffer or parse a frame of several megabytes. A supervisor's credential is checked before its upgrade is accepted, so it never sends a frame unauthenticated. A supervisor's event frames leave `threadEventEnvelopeAllowance` (1 KiB) for the envelope the control plane adds, and the control plane refuses to record an event whose frame to clients could not fit, since a recorded event that cannot be sent would break every replay.

## Protocol

The messages are defined once, as zod schemas in [`packages/protocol`](../packages/protocol), and validated wherever they cross a boundary. Both hops are WebSockets with one JSON message per frame (desktop streams excepted: they carry VNC data in binary frames); the thread and protocol version travel in the upgrade URL. The HTTP threads API is defined there too.

- **Thread events** are the durable history: the user's messages (recorded by the control plane the moment it accepts them), the agent's run starting and settling, each completed assistant message, each tool execution starting and finishing, and the repository's clone (reported by the supervisor) and publications (recorded by the control plane). Every `agent_run_started` is followed by exactly one `agent_run_settled` or `agent_failed`.
- **Stream fragments** are pieces of assistant text sent while the model produces it: relayed live, never stored, and superseded by the completed message.

| Connection                        | Direction                  | Messages                                                                                                                                                                                              |
| --------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supervisor ⇄ control plane        | Supervisor → control plane | Hello; a numbered agent or workspace event; a stream fragment; user messages delivered; a credential request; a bundle that failed; whether there is a desktop; a desktop stream that failed          |
|                                   | Control plane → supervisor | Welcome; prepare the workspace; configure model access; agent events recorded; deliver a user message; interrupt the agent; a credential; make a bundle; open a desktop stream; who holds the desktop |
| Client ⇄ control plane            | Client → control plane     | Authenticate (first, and again with each refreshed token); send a user message; interrupt the agent                                                                                                   |
|                                   | Control plane → client     | Replay announcement; a recorded thread event; a stream fragment; supervisor connection status; user message delivery status; a rejection; which viewer holds the desktop                              |
| Desktop viewer ⇄ control plane    | Viewer → control plane     | Authenticate (first, and with each refreshed token); take or give back control; then VNC data                                                                                                         |
|                                   | Control plane → viewer     | The desktop is ready, or why it is unavailable; then VNC data                                                                                                                                         |
| Desktop stream (supervisor dials) | Both ways                  | VNC data only                                                                                                                                                                                         |

## One prompt, end to end

What happens, in the code as built, when a user types a message in a thread's page and the agent replies.

1. **Web page.** The message box ([`components/message-composer.tsx`](../apps/web/src/components/message-composer.tsx)) hands the text, with an identifier minted for it once ([`connection/user-message-id.ts`](../apps/web/src/connection/user-message-id.ts)), to the thread's connection ([`connection/thread-connection.ts`](../apps/web/src/connection/thread-connection.ts)), which sends `send_user_message` on its WebSocket to `/threads/{threadId}/client`. In development, Vite's proxy forwards it to the control plane. The page shows the message as sending until its thread event comes back, and offers to send it again, under the same identifier, if it is refused or the connection drops first.
2. **Control plane, in.** The upgrade router ([`websocket/route-upgrade.ts`](../apps/control-plane/src/websocket/route-upgrade.ts)) accepted this connection in [`websocket/client-endpoint.ts`](../apps/control-plane/src/websocket/client-endpoint.ts) after checking its origin, and its session attached it to the thread once its first message authenticated a user who owns the thread. Every frame is validated ([`websocket/receive-messages.ts`](../apps/control-plane/src/websocket/receive-messages.ts)) and handed to the thread's relay ([`thread-relay/thread-relay.ts`](../apps/control-plane/src/thread-relay/thread-relay.ts)), which handles one message at a time.
3. **Recorded, then delivered.** The relay appends a `user_message` event to the thread event log, once per identifier (a message sent again that is already recorded is answered with the recorded event) ([`postgres-thread-event-log.ts`](../apps/control-plane/src/thread-event-log/postgres-thread-event-log.ts)), broadcasts it to every client watching, and only then sends `deliver_user_message`, with the message's sequence, to the thread's supervisor, so the agent never acts on a message missing from history. With no supervisor attached the message waits in history until one is.
4. **Supervisor.** The supervisor's outbound connection ([`control-plane/control-plane-connection.ts`](../apps/sandbox-supervisor/src/control-plane/control-plane-connection.ts)) validates the message and passes it to [`supervisor.ts`](../apps/sandbox-supervisor/src/supervisor.ts), which notes its sequence on disk ([`delivery/delivered-user-messages.ts`](../apps/sandbox-supervisor/src/delivery/delivered-user-messages.ts)), acknowledges it, and hands it to the Pi harness ([`pi/pi-agent-harness.ts`](../apps/sandbox-supervisor/src/pi/pi-agent-harness.ts)), which writes it to Pi's standard input as a steering `prompt` ([`pi/pi-rpc-client.ts`](../apps/sandbox-supervisor/src/pi/pi-rpc-client.ts)). Pi runs as a child process, as the agent's user where the sandbox has one ([`agent-process/`](../apps/sandbox-supervisor/src/agent-process)).
5. **Agent output, translated.** Pi answers with JSON lines. Each is parsed ([`pi/pi-records.ts`](../apps/sandbox-supervisor/src/pi/pi-records.ts)) and translated into Barrack's vocabulary ([`pi/pi-event-translator.ts`](../apps/sandbox-supervisor/src/pi/pi-event-translator.ts)): text deltas become stream fragments; the run starting, each completed message, each tool execution and the run settling become agent events. The supervisor fits each in a frame, checks it against the protocol, numbers each agent event and sends it, keeping it until the control plane confirms it recorded.
6. **Control plane, out.** The relay passes stream fragments straight to clients, keeping the current message's text so far ([`thread-relay/in-progress-assistant-text.ts`](../apps/control-plane/src/thread-relay/in-progress-assistant-text.ts)) for clients that join mid-message. It records each agent event, acknowledges it to the supervisor, and then broadcasts it.
7. **Web page, rendered.** The connection validates each message and dispatches it to the thread's store; the pure reducer ([`thread-state/thread-state.ts`](../apps/web/src/thread-state/thread-state.ts)) appends fragments to a streaming entry, replaces it with the completed message, and ignores any sequence it has already applied. React re-renders from that state.

The end-to-end tests in [`tests/end-to-end`](../tests/end-to-end) create threads through the API and run steps 2 to 6 with the real processes: with the fake agent and local-process sandboxes in `pnpm test` (including killing the control plane or the supervisor mid-run, in [`recovery.test.ts`](../tests/end-to-end/src/recovery.test.ts)), and in Docker sandboxes, with the real Pi against a mock model, in `pnpm test:docker`.
