# Deploying Barrack

> [!WARNING]
> **Nothing here has been deployed yet.** Sign-in exists: users sign in with Supabase Auth, the control plane verifies every access token itself, admits only the email addresses you list, and shows each user only their own threads. But it has never run against a real Supabase project, Railway, Daytona, a real GitHub App or a real model provider (see the [first-deployment checklist](#first-deployment-checklist)), and some limits remain: for the providers Barrack relays (Anthropic, OpenAI, OpenRouter, xAI, DeepSeek, Groq, Cerebras and Together) a user's key stays on the control plane, but for every other provider it is placed in their threads' sandboxes, where the agent (and anything a repository makes it run) can read it; a thread's branch, which the agent writes, is pushed into the user's own repository, where its continuous integration runs it with the repository's secrets (see [GitHub](#4-github-optional-private-repositories-and-pull-requests)); and the gaps the [decision log](decisions.md#2026-11-24-security-gaps-that-remain-open) still marks open (its dated notes say which) are open. Admit only people you trust with your keys and your sandbox budget.

There are two ways to run Barrack:

- **[Hosted](#hosted-railway-supabase-and-daytona)**: the control plane on Railway, Postgres on Supabase, sandboxes on Daytona. No machine of your own stays on. **Not yet tried against the real services**; start with the [first-deployment checklist](#first-deployment-checklist).
- **[On one machine](#on-one-machine-with-docker-compose)**: Postgres, the control plane and every sandbox in Docker on a machine you control, with Docker Compose, signing in through a Supabase project. **Run end to end before sign-in existed**, not since (see [what was verified](#what-was-verified)).

Both run the same image, built by the [`Dockerfile`](../Dockerfile) at the repository root: the built control plane with its production dependencies only, and the built web client, which it serves. It runs as an unprivileged user, listens on port 8787, applies database migrations at startup, and on SIGTERM closes its connections, waits for sandbox creations under way and exits. It is configured entirely by environment variables. It carries Git, with which it checks and pushes the branches threads publish, under limits on memory, processor time, wall time and disk; the memory limit can be applied only on Linux, and the control plane says at startup if any cannot be applied. Its `control-plane-with-docker-cli` stage adds the Docker CLI, which only the Docker sandbox provider needs.

## Hosted: Railway, Supabase and Daytona

### What it costs

For one or two people with a few threads, about 40 sandbox-hours a month, as researched on **2026-11-24** (prices change; check each service's pricing page):

| Service                                                | Estimate                                                                                                                                                                                                       |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Railway Hobby plan, control plane (~0.1 vCPU, ~256 MB) | $5 a month, which includes $5 of usage that covers it                                                                                                                                                          |
| Daytona, 40 h at 2 vCPU and 4 GiB ($0.1656 an hour)    | about $6.60, paid from Daytona's one-time $200 of free credit while it lasts (about 1,200 such hours); stopped sandboxes are archived after an hour, which ends their disk charge                              |
| Supabase Free plan                                     | $0, but a free project pauses after a week of too little database activity; the control plane's [keep-alive](../apps/control-plane/README.md#supabase) prevents that. Supabase Pro, which never pauses, is $25 |
| **Total**                                              | **about $5 a month** while the Daytona credit lasts, then about $12                                                                                                                                            |

Model usage is billed to each user by their own model provider, on the keys they add in Settings; Barrack pays for none of it.

**The live desktop's bandwidth is Railway egress.** Every byte of a desktop someone watches passes through the control plane (see [the architecture](architecture.md#the-live-desktop)), at Railway's $0.05 per GB. Measured on 2026-11-24 with one viewer: a still screen sends nothing; watching an agent open a browser and click through a page is a fraction of a megabyte a minute, well under a cent an hour; continuous full-screen motion (video, scrolling) sends 0.6 to 3.5 MB/s, 2 to 13 GB an hour, $0.11 to $0.64 an hour. Each viewer, a phone beside a laptop say, costs as much again. A hidden tab streams nothing.

**Put Railway, Daytona and Supabase in the same region.** Desktop pictures and the keystrokes of a user in control travel browser → control plane → sandbox and back; the control plane in another continent than the sandboxes adds the round trip between them (70 to 150 ms) to every keystroke. The same holds, less visibly, for the thread's messages.

### 1. Supabase: the database

1. Create a project on the Free plan, in the region closest to the Railway region you will use. Keep its database password.
2. Open the project's **Connect** panel, choose **Session pooler**, and copy the string: `postgresql://postgres.<project-ref>:<password>@aws-<n>-<region>.pooler.supabase.com:5432/postgres`. Put the password in it, [percent-encoding](https://en.wikipedia.org/wiki/Percent-encoding) any of `@ : / ? # & %` or spaces, and add no query parameters (the control plane refuses them). This is `BARRACK_DATABASE_URL`.
   - Why the session pooler: the direct host is IPv6 only on the Free plan, and Railway services have no outbound IPv6 unless it is turned on; the pooler is IPv4 on every plan, and session mode (port 5432) keeps the session that migrations' advisory lock needs. The transaction pooler (port 6543) does not. [Supabase: connecting to Postgres](https://supabase.com/docs/guides/database/connecting-to-postgres).
3. Under **Database settings → SSL configuration**, download the certificate. Its contents are `BARRACK_DATABASE_CA_CERTIFICATE`: Supabase signs with its own authority, and the control plane verifies the server's certificate and host name (`verify-full`) against it. You can also turn on **Enforce SSL on incoming connections** there.

The control plane creates its tables in a schema of its own, `barrack`, with row level security on and no policies, so Supabase's Data API serves nothing from them. More in the [control plane's README](../apps/control-plane/README.md#supabase).

### 1b. Supabase: sign-in

The same project signs users in. The web client asks for a six-digit code by email and hands the control plane the access token Supabase gives it; the control plane checks it against the project's published public keys, so it never needs a secret key. In the project's dashboard:

1. **Asymmetric signing keys.** Under **Project Settings → JWT Keys**, the current key must be asymmetric (ECC P-256 is recommended). New projects have one; a project still on the legacy HS256 secret must rotate to one. The control plane fetches the public keys at startup and refuses to start, saying so, if there are none. Until it has read them it does not listen; while Supabase cannot be reached, or answers with anything but a key set, it logs each attempt and tries again, for as long as it takes, as it does for the database.
2. **The code in the email.** Under **Authentication → Email Templates**, edit the **Magic Link** template to include `{{ .Token }}`, the code, for example `<p>Your Barrack code: {{ .Token }}</p>`. No redirect URLs are needed.
3. **Mail for everyone else.** Supabase's built-in sender delivers only to the project's team members, about twice an hour. For anyone outside the team to sign in, set up custom SMTP under **Authentication → SMTP Settings**.
4. **Sign-ups off.** Supabase lets anyone sign up by default. List the addresses that may use Barrack in `BARRACK_ALLOWED_USER_EMAILS` (the control plane refuses everyone else, once Supabase confirms they own their address), and once each of them has signed in once, turn off **Allow new users to sign up** under **Authentication → Sign In / Providers**. Leave "Confirm email" on and anonymous sign-ins off, as they are by default.
5. **The publishable key only.** Under **Project Settings → API Keys**, copy the project URL (`BARRACK_SUPABASE_URL`) and the **publishable** key, `sb_publishable_…` (`BARRACK_SUPABASE_PUBLISHABLE_KEY`). It is handed to every browser. Never use the secret key or the legacy `service_role` key: the control plane refuses to start with one.

How the control plane checks each token is in the [control plane's README](../apps/control-plane/README.md#signing-users-in).

### 2. Daytona: the sandbox image

1. Create a Daytona account and an API key (`DAYTONA_API_KEY`).
2. Build the [sandbox image](../sandbox-image/README.md) for `linux/amd64`, which Daytona requires, with a tag of its own (Daytona rejects `latest`):

   ```sh
   docker build --platform linux/amd64 --file sandbox-image/Dockerfile --tag barrack-sandbox:$(git rev-parse --short HEAD) .
   ```

   Build it from the same revision as the control plane. A supervisor speaks one protocol version, and the control plane refuses any other, so a snapshot from an older build cannot connect: its supervisor exits saying which version was expected. The image also gives the supervisor a state directory of its own, `/var/lib/barrack/supervisor` (`BARRACK_SUPERVISOR_STATE_DIRECTORY`), where it records how far the agent has been handed user messages; a custom image must provide one that only the supervisor's user can write.

3. Push it as a snapshot with Daytona's CLI, choosing a new name for each build. Its name is `BARRACK_DAYTONA_SNAPSHOT`. A snapshot carries the size of the sandboxes made from it; see the command's `--help` for CPU, memory and disk (2 vCPU, 4 GiB and 8 GiB suit an agent).

   ```sh
   daytona snapshot push barrack-sandbox:<tag> --name barrack-sandbox-<tag>
   ```

**Tiers and network access.** On Daytona's Tier 1 (email verified) and Tier 2 (card added, $25 top-up), a sandbox can reach only Daytona's list of [essential services](https://www.daytona.io/docs/en/network-limits): package registries, GitHub, the major model providers, `*.supabase.co`, and `*.railway.app`, among others. So:

- The control plane must be reached at its **generated `*.up.railway.app` domain**. A custom domain of your own is not on the list and sandboxes could not connect to it.
- The agent cannot browse arbitrary websites, in its desktop's Firefox or otherwise: only the sites on that list and pages served inside the sandbox. Full internet access starts at Tier 3, which needs a $500 top-up. The desktop itself needs nothing more: its stream is a second connection to the control plane's own domain.
- Tier 1 pools a small allowance across running sandboxes (around 10 vCPU and 30 GiB of storage); each sandbox has at most 4 vCPU, 8 GiB of memory and 10 GiB of disk. A stopped sandbox holds storage until it is archived.

The Daytona provider turns Daytona's auto-stop off (it ignores an agent working inside the sandbox) and archives stopped sandboxes after `BARRACK_DAYTONA_AUTO_ARCHIVE_MINUTES`; see the [providers' README](../packages/sandbox-providers/README.md).

### 3. Railway: the control plane

The service is described as code in [`.railway/railway.ts`](../.railway/railway.ts), Railway's Infrastructure as Code, which replaced `railway.json` (deprecated; existing files stop being read on 2026-12-01). Railway does not read it when deploying: the Railway CLI applies it to your project. It sets the Dockerfile builder, the health check on `/health`, exactly one replica, no sleeping when idle, a 120-second drain for the control plane's shutdown with no extra overlap (two instances still run at once on every redeploy; see [two instances at once](#two-instances-at-once)), restarting after a crash, and every variable that is not a secret. The comments in the file say why for each. Use the Hobby plan or above: the Free plan runs services serverless, putting them to sleep when idle.

1. Create an empty project in Railway's dashboard.
2. With the [Railway CLI](https://docs.railway.com/cli) (5.42.1 or newer), from the repository root after `pnpm install`:

   ```sh
   railway login
   railway link            # choose the project and its environment
   railway config plan     # read what it will create
   railway config apply
   ```

   This creates the `control-plane` service. Read every later plan too: it marks any variable or setting it would delete.

3. In the service's settings, connect your GitHub repository (the root directory is the repository root). Railway finds the root `Dockerfile` and builds its last stage.
4. Under **Networking**, generate a domain for port 8787. The variables refer to it as `${{RAILWAY_PUBLIC_DOMAIN}}`, so generate it before the first deploy.
5. Under **Variables**, set the values marked "dashboard" below (the raw editor accepts the multi-line certificate), `BARRACK_MODEL_CREDENTIAL_KEY` among them (see [users' model keys](#users-model-keys-and-the-key-that-seals-them)). Sealing them hides them from the dashboard and API afterwards.
6. Deploy.

### 4. GitHub (optional): private repositories and pull requests

Without this step, threads can start from public repositories, cloned without credentials, and nothing can be published; the settings page and the new-thread form say that GitHub is not set up. With it, users connect their GitHub account in Settings, start threads on their own repositories, and push a thread's branch or open a pull request from the thread's page. How it works, and what it does not protect against, is in the [architecture](architecture.md#working-with-a-git-repository) and the [decision log](decisions.md).

Register a GitHub App for your installation (on GitHub: **Settings → Developer settings → GitHub Apps → New GitHub App**, or the same under an organisation's settings), with exactly these settings, `<domain>` being the control plane's public domain:

| Setting                                                | Value                                                                                                   | Why                                                                                                                                                                                                                                                  |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Homepage URL                                           | `https://<domain>`                                                                                      | GitHub requires one.                                                                                                                                                                                                                                 |
| Callback URL                                           | `https://<domain>/github/callback`                                                                      | The web client's page that finishes connecting. It must be the first callback URL: Barrack sends no `redirect_uri`, so GitHub uses the first.                                                                                                        |
| Expire user authorization tokens                       | on (the default)                                                                                        | Barrack revokes the user's token as soon as it has read their repositories, and never stores it; expiry is a second fence.                                                                                                                           |
| Request user authorization (OAuth) during installation | **off**                                                                                                 | That flow comes back without the single-use `state` Barrack ties each sign-in to, and would be refused. Barrack starts the sign-in itself.                                                                                                           |
| Enable Device Flow                                     | off                                                                                                     | Not used.                                                                                                                                                                                                                                            |
| Setup URL                                              | `https://<domain>/?page=settings`, with **Redirect on update** on                                       | After installing, users land in Settings and connect. The `installation_id` GitHub adds is ignored: it can be spoofed, and Barrack asks GitHub which installations the user can reach instead.                                                       |
| Webhook                                                | **Active** off                                                                                          | Barrack uses no webhooks.                                                                                                                                                                                                                            |
| Repository permissions                                 | **Contents: Read and write**, **Pull requests: Read and write**, **Metadata: Read-only**                | Read for the sandbox's clone, write for the control plane's push, pull requests to open one, metadata to check the user may still push. Nothing else, and never **Workflows**: without it, GitHub refuses any push that changes `.github/workflows`. |
| Organization and account permissions                   | none                                                                                                    |                                                                                                                                                                                                                                                      |
| Where can this GitHub App be installed?                | **Only on this account** if every repository is yours or this organisation's; otherwise **Any account** | GitHub lets a private App be installed only on the account that owns it. A public App grants nothing by itself: only users of this installation who connect their GitHub account in Barrack can use it, and only on repositories they can push to.   |

Then, on the App's page:

1. Note the **Client ID** (`BARRACK_GITHUB_APP_CLIENT_ID`) and the App's URL name, the last part of `https://github.com/apps/<slug>` (`BARRACK_GITHUB_APP_SLUG`).
2. **Generate a new client secret** (`BARRACK_GITHUB_APP_CLIENT_SECRET`).
3. **Generate a private key**, which downloads a `.pem` file. Its whole contents are `BARRACK_GITHUB_APP_PRIVATE_KEY`; a dashboard that stores it on one line, with `\n` for each line break, works too. Keep no other copy.
4. Set the four in Railway's dashboard, sealed; `.railway/railway.ts` preserves them. All four or none: the control plane refuses to start with some only.
5. **Install App**, on the repositories threads may work on. Users then connect GitHub in Barrack's Settings.

GitHub's [manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest) can register an App from a description in one click, but it hands the private key and secrets back to a page of the registering application, which would then have to store them or show them once to be pasted into these variables, and redeploy: no fewer steps for something done once, and a route that receives the App's key. Registering by hand was chosen instead.

What to set on GitHub besides, since Barrack cannot enforce it:

- **Protect the default branch** (and any branch that deploys) with a ruleset or branch protection requiring a pull request. Barrack pushes only to `barrack/<thread>` and the sandbox holds no token that can write, but these rules guard against everything else. On a private repository they need a paid GitHub plan.
- **Keep repository secrets from untrusted branches.** A thread's branch lives in the repository itself, so a workflow triggered by `push` or `pull_request` runs the agent's code with the secrets branches of the repository get, which a fork's pull request would not. Put deployment secrets in [environments](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment) with required reviewers, or keep workflows that hold secrets off branches matching `barrack/*`.
- **Two people for a merge**, if you want one: the pull request is opened by the App, so the user who asked can approve it alone; require two approvals or code owners to prevent that.

#### Two instances at once

Every redeploy runs the old and the new control plane side by side. Railway starts the new deployment and switches traffic to it only once its health check answers, which the control plane does only after migrating the database; until then the old one serves everything, while the new one has already migrated and started its lifecycle sweeps. Once traffic has moved, the old one is sent SIGTERM (at once, since `overlapSeconds` is 0) and has up to `drainingSeconds` (120) to finish. Setting no overlap shortens this, but nothing removes it ([health checks](https://docs.railway.com/deployments/healthchecks), [teardown](https://docs.railway.com/deployments/deployment-teardown)). What each shared part does about it:

- **Migrations** run in the new instance while the old one still serves, one instance at a time under an advisory lock. So a migration must leave the previous release working: add columns and indexes, and rename or drop only in a later release, once nothing uses the old shape. Every migration from `0040` to `0120` only adds. `0030`, which introduced the thread lifecycle, does not (it replaces the sandbox states and constraints, so a control plane from before it cannot create a thread once it has run); nothing has been deployed yet, so no installation meets that. Nor does any meet the other way an order can break: a database must have applied exactly this build's first migrations, so one migrated by a build that had `0050` and `0060` but not `0040` (written at the same time on another branch) would be refused rather than migrated out of order. An index is built inside its migration's transaction, which holds back writes to its table until it is built: `0130`'s, on `thread_events`, would hold up every event appended during a redeploy if that table were large, which it is nowhere yet, since nothing has been deployed. A later migration adding an index to a large table must build it `concurrently`, and the migration runner cannot do that yet: it runs each migration in a transaction, inside which Postgres refuses a concurrent build, so such a migration needs the runner to run it outside one first.
- **Sandbox operations, idle shutdown and reconciliation** change a thread only by a compare-and-set on its version; an operation holds a lease that the instance doing it renews, so the other takes it over only once that instance has gone; idle shutdown stops a sandbox only if no activity was recorded since it looked; and a run is closed by an append conditional on that run still being open. Neither instance can undo or repeat what the other did.
- **History** is safe with two writers: sequences are gapless whoever appends, and a supervisor's event, a user's message or a publication's outcome is recorded once however many times it arrives.
- **Connections** are each relayed by the instance holding them. Until the old instance closes its connections on SIGTERM, a supervisor can be attached to one and a browser to the other. Events still reach the browser (it replays what it was not sent), but a message sent through the instance without the supervisor waits, shown as waiting, until the supervisor reconnects a moment later; and a stop or an interrupt made through it does not reach the agent first (a stop goes ahead, and closes the run in history). Publishing is the same: the instance asked to publish waits, in its own memory, for the supervisor's upload, which during the overlap may reach the other instance and be refused; the publication then fails with a reason, is recorded once, and can simply be asked for again.
- **The database** gets five connections from each instance, within the pooler's default of fifteen; the keep-alive query runs in both, which is harmless.

### What the first real run must check

Each check says how to tell that it passed. A check that fails is a bug to report, or a document to correct.

**Railway**

1. **Infrastructure as Code.** `.railway/railway.ts` type-checks against the `railway` SDK (3.16.0) and evaluates to the expected service, but has never been planned or applied. If the plan refuses a `preserve()` of a variable not yet set, set the secrets in the dashboard first and apply again.
2. **The build.** The image has been built here only with base images carrying a local proxy's certificate authority, and in CI with the real ones. Passed if the build log says it used the Dockerfile.
3. **Port and health check.** Passed if the deploy log shows, as JSON lines, `Applied a database migration` (once per migration, the first time), `Querying the database at this interval…` with `keepAliveIntervalInMinutes: 240`, `Creating thread sandboxes` with `sandboxProvider: "daytona"`, and `Control plane listening` on `0.0.0.0:8787`; the deployment turns active; `https://<domain>/health` answers `{"status":"ok"}`; and `https://<domain>/` asks you to sign in.
4. **A redeploy.** Passed if, with a thread open, a redeploy keeps its whole history; the new deployment migrates and passes its health check while the old one still serves; the old deployment's log ends with `Shut down cleanly` within the 120-second drain; and the new log shows `Supervisor connected` for the thread. If the old instance was in the middle of creating, stopping or starting a sandbox, the new log shows `Taking over a sandbox operation…` within two `BARRACK_SANDBOX_CHECK_SECONDS`.
5. **WebSockets through Railway.** Railway is documented to keep WebSockets open indefinitely and to end plain HTTP responses after 15 minutes; neither has been seen. Passed if a thread page left open for more than 15 minutes, while its agent is idle and while it works, does not reconnect (the control plane's log shows no new `Supervisor connected`, and the page never shows the agent as not connected), and the live desktop stream stays open as long. The 15-minute cut of a relayed model answer is check 3 under model providers.

**Supabase**

1. **The database.** Passed if the control plane starts at all: it refuses to start, naming the variable to fix, if the session pooler refuses the connection with `verify-full` against the downloaded certificate. In the table editor, the `barrack` schema then holds `users`, `threads`, `thread_events`, `thread_sequence_counters`, `thread_repositories`, `github_connections`, `github_connection_attempts`, `model_credentials`, `model_proxy_tokens`, `model_usage`, `model_usage_caps`, `model_switch_allowances` and `schema_migrations`.
2. **Staying awake.** Supabase does not define "sufficient activity", and emails a warning about a week before pausing a project. Passed if no such email arrives in the first weeks of an installation nobody uses.
3. **Tokens checked against the project's real published keys.** Sign-in has run only against the tests' stand-in for Supabase Auth, which signs tokens the way Supabase documents. Passed if the control plane starts (it refuses, saying so, if the project publishes no asymmetric key); a code arrives by email for a listed address, through custom SMTP for an address outside the project's team; signing in with it shows the thread list; another address, once confirmed, is told it is not allowed (the check against Supabase's `/auth/v1/user`); and a thread page left open for more than an hour, while supabase-js refreshes the token, stays connected.

**Daytona**

1. **The snapshot.** Passed if `daytona snapshot push` (Daytona's CLI for its generally available platform may be installed as `daytona` or `daytona-v0`) accepts the image under its tag, with the size flags its `--help` shows (2 vCPU, 4 GiB and 8 GiB suit an agent), and a thread created afterwards gets a sandbox in Daytona's dashboard. Fix the commands in [step 2](#2-daytona-the-sandbox-image) if they differ.
2. **The supervisor's token, and which user Daytona writes files as.** The provider uploads the token to `/var/lib/barrack/secrets/BARRACK_SUPERVISOR_TOKEN` with Daytona's file API and sets it to `barrack-supervisor`, mode 0400, which works only if Daytona's daemon writes as root or as `barrack-supervisor`. Passed if the log shows `The thread's sandbox is running` and then `Supervisor connected` for the thread, and a command run through Daytona's command interface, `stat -c '%U %a %n' /var/lib/barrack/secrets /var/lib/barrack/secrets/BARRACK_SUPERVISOR_TOKEN`, prints `barrack-supervisor 700` and `barrack-supervisor 400`. If the supervisor refuses to start, it says why in `/var/log/barrack/supervisor.log`, and the thread page quotes it.
3. **Which user Daytona runs commands as, and what they see.** Passed if `id -un` through Daytona's command interface prints `barrack-supervisor` (the image's user), not `root`; and neither the sandbox's `envVars`, its record in Daytona's API, nor `env` run through the command interface holds `BARRACK_SUPERVISOR_TOKEN`.
4. **Whether the agent can reach Daytona's daemon.** The daemon listens inside every sandbox. If a process there can ask it to run a command or write a file without the API key, the agent can become any user, root included, and the separation between supervisor and agent does not hold. Find the daemon's port (`ss -ltnp` through the command interface) and, as `barrack-agent` (for example, ask the agent of a thread to try), send it a request to run a command. Passed if every such request is refused. If one is accepted, run nothing of Barrack's on Daytona until it can be refused (see the open gaps in the [decision log](decisions.md#2026-11-24-security-gaps-that-remain-open)).
5. **The image's environment.** Passed if the thread page shows the desktop rather than "This sandbox has no desktop": that means Daytona passed the image's `BARRACK_DESKTOP_COMMAND` and `DISPLAY` to the supervisor.
6. **The desktop under Daytona's runtime.** Daytona's seccomp profile has not been examined. Passed if the desktop shows a picture, **Take control** works, and Firefox opens an allowed page when the agent is asked to open one.
7. **The network.** On Tiers 1 and 2 a sandbox reaches only Daytona's list of essential services. Passed if the supervisor's WebSocket to `*.up.railway.app` connects and stays open, and the desktop stream, a second connection to the same domain, does too.
8. **Stopping, archiving and starting.** Passed if: stopping a thread while its agent works ends the run in the thread's history (Daytona's stop is not known to send a signal the supervisor can act on; the control plane interrupts the agent first and closes a run left open, so history stays right either way); a thread stopped for longer than `BARRACK_DAYTONA_AUTO_ARCHIVE_MINUTES` wakes with its files and its conversation (its next answer knows what was said before), while the page shows "Waking the sandbox…" (note how long it takes); an archived sandbox's thread shows as stopped, and one deleted in Daytona's dashboard shows as failed and gone; and stopped or archived sandboxes no longer count against the organisation's running resources (they still count against storage until deleted).

**GitHub** (every flow ran only against the tests' stand-in, which answers as GitHub's documentation describes)

1. **Linking.** Passed if **Connect GitHub** in Settings goes to GitHub, comes back to `/github/callback` with a code and the state, and finishing it lists your repositories.
2. **Cloning a private repository.** Passed if a thread on one of them reports its clone, and the agent, asked to push with the token Git's helper gives it, is refused by GitHub.
3. **Publishing.** Passed if **Push branch** pushes `barrack/<thread>`, **Open pull request** opens one pull request as the App, and a later publication updates the same pull request rather than opening a second.
4. **Workflows.** Passed if publishing a commit that changes `.github/workflows` is refused by GitHub, with a message the thread shows. GitHub's new, longer token format (rolling out since 2026-04-27) fits every limit here, but has not been seen.

**Model providers through the proxy**

1. **Threads answer.** Nothing has run against a real provider. The proxy's formats, usage and error bodies follow Anthropic's and OpenAI's API references and were exercised against the mock model speaking them, with the real Pi. Passed if, with a real Anthropic and a real OpenAI key (each with a spending limit), a thread answers through the proxy; usage in Settings matches the provider's own usage page; and a revoked key is reported as rejected.

## Users' model keys, and the key that seals them

Each user adds their own API key for each model provider they use, in the web client's Settings, and chooses a model for each thread; every thread runs on its owner's key for its model's provider, and Barrack pays for no model use. How the keys travel, and what the agent can do with one, is in the [architecture](architecture.md#each-users-own-model-access).

The control plane stores each key sealed with AES-256-GCM under `BARRACK_MODEL_CREDENTIAL_KEY`, which the database never holds, so a copy of the database alone yields no key.

- **Making the key.** `openssl rand -base64 32`, once per installation: base64 of 32 random bytes. Set it as a secret where the control plane runs, and keep a copy somewhere safe, apart from the database's backups.
- **Losing it** loses every stored key: they cannot be opened without it. The control plane refuses to start while any stored key was sealed under a key it was not given, naming how many and the fingerprint of the key that sealed them, since the usual cause is a mistyped or forgotten variable, and starting anyway would leave those users' threads quietly unable to run. If the key is truly lost, delete the stored keys (`delete from barrack.model_credentials;`, or only the rows with the fingerprint named) and ask users to add theirs again; nothing else is lost.
- **Replacing it** (rotation), in two deploys:
  1. Set the new key as `BARRACK_MODEL_CREDENTIAL_KEY` and the old one as `BARRACK_MODEL_CREDENTIAL_PREVIOUS_KEYS`, and deploy. The new instance seals every stored key again under the new key at startup, then every five minutes. While the old instance drains, it holds only the old key: it cannot open what the new one sealed again, and leaves running sandboxes the keys they already have rather than withdraw them; a key a user saves through it is sealed under the old key, and the new instance's next pass seals it again.
  2. Once the old deployment has stopped, wait for the new instance to log `Every stored model credential is sealed under the current key` after that (within five minutes), or check that `select key_fingerprint, count(*) from barrack.model_credentials group by 1;` shows only the new key's fingerprint, which the log names. Then remove `BARRACK_MODEL_CREDENTIAL_PREVIOUS_KEYS` and deploy again. Removing it earlier risks a key still sealed under the old one, and the control plane then refuses to start, naming the old fingerprint: put the old key back and wait for the log line.

  To roll back to the old key, swap the two: the old as `BARRACK_MODEL_CREDENTIAL_KEY` and the new as `BARRACK_MODEL_CREDENTIAL_PREVIOUS_KEYS`, and follow the same two steps.
- **Keys kept on the server.** For Anthropic, OpenAI, OpenRouter, xAI, DeepSeek, Groq, Cerebras and Together, the key never leaves the control plane: the agent's requests to the provider go through the control plane's model proxy, which adds the key ([architecture](architecture.md#the-model-proxy)). The sandbox holds a token that works only at the proxy, for its own thread and provider and the thread's own model, while the thread runs, and is revoked when it stops. Settings marks these providers "Your key stays on the server".
- **Keys placed in the sandbox.** For every other provider, a thread's sandbox receives its owner's key while it runs, as a file only the agent's user can read; nothing started in the sandbox from outside finds it in its environment. The agent itself can read it, and so can any code a repository makes the agent run: anyone who starts threads on repositories they do not trust should prefer a relayed provider, or use a key with a spending limit. Settings marks these providers "Your key is placed in the sandbox".

## Model usage and caps

Barrack counts the tokens each user's threads use; it prices nothing, since each user pays their provider. For relayed providers the proxy measures usage from the provider's own answers; for the others it is what the agent in the sandbox reports, which is shown but not trusted. Users see their last 30 days by model in Settings, and each thread's total on its page.

- **An installation cap.** `BARRACK_MODEL_USAGE_CAP_TOKENS` caps every user's tokens (input, output and cache together, as counted at the proxy) over the last `BARRACK_MODEL_USAGE_CAP_WINDOW_HOURS` hours (24 by default). Unset, there is no cap. Each user may set a lower cap of their own in Settings.
- **What a cap does.** Once a user reaches it, the proxy refuses their threads' requests to relayed providers: a running thread's run ends with a message saying the cap is reached, and new messages to threads on those providers are refused, until older usage leaves the window. Requests in flight are ended within 30 seconds; what they used before they end still counts, so usage can go past the cap by what up to four requests per thread use. Every request the provider received whole is counted however it ends, the control plane shutting down included (unless its 30 seconds of grace run out, or the usage write is still lost after its retries); where the answer did not give the provider's figures it is estimated, meant to err high: a request the agent abandons before the answer begins at the most output it allowed, and a streamed answer cut short on a model that may reason unseen at that maximum too, so a user who stops a thread mid-answer on a reasoning model is counted high. Requests that would leave the provider generating unseen (OpenAI's background responses, xAI's deferred completions) are refused, and so are requests that send a document or file or refer to input the provider keeps or fetches (earlier responses, conversations, stored prompts, files, remote MCP servers), OpenRouter routing that could answer with another model, and every OpenRouter plugin.
- **What a cap cannot do.** It limits the tokens spent through the proxy; it is not a guarantee about anyone's bill. It counts tokens only: a provider's per-call charges for its own tools (web search, code execution containers and the like), which a request can ask for, are neither counted nor bounded, and a provider that runs several turns of its own within one request (xAI's `max_turns`, provider-run tools) bills the input again for each, which an estimate does not. Some of what it counts is estimated, and a provider can bill more than the estimate for an answer cut short, for an image sent at OpenAI's `original` detail, or for reasoning a model did though the request said not to. Usage whose write still fails after three more tries is logged as lost; a write whose acknowledgement is lost is counted twice. For providers whose keys are placed in the sandbox the agent calls the provider itself: no cap can be enforced there, and their usage, only reported by the sandbox, does not count towards it. Users should set a spending limit with each provider too; Settings says so.
- **What a request may contain.** The proxy relays only the thread's own model, checks a few fields of each body and refuses what it could not count (above), and keys spelt so that a decoder matching names regardless of case might read them differently; otherwise it passes bodies through unchanged. A request cannot refer to stored earlier responses, conversations, stored prompts, files or documents, or remote MCP servers; it can still give an image by its address or file identifier, which the provider fetches and which is counted at 5,000 tokens like any image.
- **Callers without a token.** Anyone can send the proxy requests naming any thread. Their token lookups are bounded for the whole instance (32 at once, 200 in a burst, 100 a second), so a flood of wrong tokens can make an agent's first request after the control plane starts, or after more than 30 seconds in which none of its requests began or ended on that instance, wait as busy; the agent retries a few times over about 15 seconds and its run then ends with an error the user can send again. A token accepted by a lookup stays remembered while its requests begin or end at least every 30 seconds, and is let in outside the bound (looked up again, outside it, once 15 seconds have passed since its last lookup), so a flood cannot hold up an agent at work. Nothing past that bound is per caller; limiting a flood itself is for the hosting provider's edge.
- **The bytes requests hold.** `BARRACK_MODEL_PROXY_REQUEST_BODIES_MEBIBYTES` bounds the request bodies held at once; one thread may hold a quarter of it and one owner half, never less than one 32 MiB body. These limit; they reserve nothing. At the default of 128 one user cannot hold more than half, but two users together can hold it all (their agents then answer busy, and retry); at the smallest allowed, 32, one thread can.
- **Bandwidth and Railway's limit.** Every relayed request and answer passes through the control plane. Answers, which are Railway's billed egress, are small beside the live desktop's traffic; requests carry the conversation inbound. Railway ends a plain HTTP response after 15 minutes, so an answer streamed for longer is cut and the agent retries it; such long answers are rare.

## On one machine with Docker Compose

[`compose.yaml`](../compose.yaml) runs Postgres, the control plane and a Docker socket proxy; the control plane creates each thread's sandbox as a sibling container on the same Docker. It needs Docker Engine with Compose 2.24 or newer, on Linux or Docker Desktop.

1. Build the sandbox image (`barrack-sandbox:dev`): `pnpm sandbox-image:build`, or without Node, `docker build --file sandbox-image/Dockerfile --tag barrack-sandbox:dev .`
2. Set up a Supabase project for sign-in as in [step 1b](#1b-supabase-sign-in); this path needs no Supabase database. Development mode's single shared user is refused here, because the control plane listens on every interface of its container, where sandboxes can reach it.
3. Write a `.env` file beside `compose.yaml` (it is ignored by Git):

   ```sh
   BARRACK_DATABASE_PASSWORD=<letters and digits>
   BARRACK_SUPABASE_URL=https://<project-ref>.supabase.co
   BARRACK_SUPABASE_PUBLISHABLE_KEY=sb_publishable_…
   BARRACK_ALLOWED_USER_EMAILS=you@example.com
   BARRACK_MODEL_CREDENTIAL_KEY=<what `openssl rand -base64 32` prints; keep a copy>
   # To try it without a model: BARRACK_AGENT_HARNESS=fake
   ```

   Compose refuses to start without the first five. Each user then adds their own model keys in Settings (see [users' model keys](#users-model-keys-and-the-key-that-seals-them)). For private repositories and pull requests, also register a GitHub App as in [step 4](#4-github-optional-private-repositories-and-pull-requests) and add its four `BARRACK_GITHUB_APP_` variables here.

   Every variable in it reaches the control plane, so the control plane's other settings ([its README](../apps/control-plane/README.md#configuration)) can go here too. With rootless Docker, also set `DOCKER_SOCKET` to its socket's path.

4. `docker compose up --build --detach`, then open <http://localhost:8787/> and sign in.

The port is published on `127.0.0.1` only. To use it from another machine, forward it over SSH (`ssh -L 8787:127.0.0.1:8787 <host>`), or put it behind a reverse proxy that serves HTTPS, since access tokens must not cross a network in the clear, and add that origin to `BARRACK_ALLOWED_CLIENT_ORIGINS`.

After upgrading Barrack, rebuild the sandbox image too (step 1): a sandbox from an image built before the upgrade may speak an older protocol version, which the control plane refuses.

**Stopping.** Sandboxes are not part of the Compose project, so remove them first, then the rest; `--volumes` also deletes the database:

```sh
docker ps --all --quiet --filter label=barrack.sandbox | xargs -r docker rm --force
docker compose down
```

### What can reach what

| Network      | Members                                   | Internet              |
| ------------ | ----------------------------------------- | --------------------- |
| `database`   | Postgres, the control plane               | none (internal)       |
| `docker-api` | the socket proxy, the control plane       | none (internal)       |
| `sandboxes`  | the control plane, every thread's sandbox | yes, for agents' work |

A sandbox reaches the control plane as `ws://control-plane:8787`, and the internet. It cannot reach Postgres or the socket proxy, whose networks it never joins, and the Docker socket is not in it. Sandboxes can reach each other, as they could on Docker's default bridge, and, like any container, services on the host that listen on all interfaces, and the cloud metadata address (below).

### The cloud metadata address

> **On a cloud VM, block this before running agents.** A sandbox can reach `169.254.169.254`, where most clouds (AWS, Google Cloud, Azure, DigitalOcean, Hetzner and others) answer the machine's own metadata, and on several of them hand out credentials for the machine's cloud account. Any agent, or anything it downloads, could read them. Nothing in Compose or in Barrack stops it: Docker gives no per-network way to refuse one destination.

The Compose file names the sandboxes' bridge interface `barrack-sandbox`, so one rule on the host, in Docker's `DOCKER-USER` chain (which Docker consults for all traffic it forwards and never flushes), refuses that address to sandboxes alone:

```sh
sudo iptables -I DOCKER-USER -i barrack-sandbox -d 169.254.169.254 -j REJECT
```

It holds across `docker compose down` and `up`, since the interface keeps its name, but not across a reboot: save it with your distribution's mechanism (for example `iptables-save` with the `iptables-persistent` package on Debian and Ubuntu), or run it from a unit that starts after Docker. On AWS, also refuse `169.254.170.2` (container credentials) and, if the sandbox network ever gets IPv6, `fd00:ec2::254`. To check it, from a sandbox (`docker exec --user barrack-agent <container> node -e …` connecting to `169.254.169.254` on port 80) the connection should be refused while the internet still answers.

This rule was tested on 2026-11-24 with Docker 29.9 and its default `iptables` firewall backend, on a network declared exactly as in `compose.yaml`: before it, a container on the network got an answer from `169.254.169.254`; after it, the connection was refused, for root and for an unprivileged user alike, while `1.1.1.1:443` still connected, and it still applied after the network was removed and created again. With Docker's `nftables` backend (`docker info` shows `Firewall Backend: nftables`) there is no `DOCKER-USER` chain; an equivalent rule in a table of your own was not tested.

### The Docker socket

Whoever can create containers through Docker's API can start one that is privileged or mounts the host's files, and so controls the host as root. The control plane must create containers, so **a flaw in the control plane could become control of the machine.** Run this only on a machine you would trust it with. Two things narrow the exposure:

- The control plane never holds the socket. It reaches Docker through [wollomatic/socket-proxy](https://github.com/wollomatic/socket-proxy), which answers only the control plane and forwards only the calls the Docker provider makes: create a container; start, stop, remove and inspect a container named by its full 64-character ID, put files into one (`docker cp -`, which hands a new sandbox's supervisor its token), and read its log (the end of a failed sandbox's, where its supervisor says why it stopped); inspect a container named `barrack-thread-…`; and the version check. Listing containers, `exec`, pulls, builds, volumes and networks are refused. The proxy holds no capabilities and has a read-only filesystem.
- **These calls are not limited to sandboxes.** The proxy matches only the request's path and cannot tell a sandbox from any other container by its ID, so it would let the control plane start, stop, remove, inspect, read the log of or write files into any container, Postgres's included, whose full ID it had. What keeps it to its own sandboxes is that it cannot list containers: the full IDs it can know are those `docker container create` gave it, and its own, which a process can read inside its container. A container ID is 256 random bits, so another container's cannot be guessed. (The proxy offers no way to filter by the target container's labels, so the rules cannot name sandboxes only.)

The proxy does not look inside a create request, so it cannot stop a privileged one; a check showed it accepting one. Filtering request bodies, or a Docker authorization plugin, would close that and is not done.

### What was verified

On 2026-11-24, on one Linux machine with Docker 29.9 and Compose 5.7, building with local base images that carry a proxy's certificate authority (the build arguments `NODE_IMAGE`, `RUNTIME_BASE_IMAGE` and `DOCKER_CLI_IMAGE` replace the base images; nothing about that is committed):

- The image alone, against a throwaway Postgres: migrations applied, `/health` answered `{"status":"ok"}`, `/` served the web client, a thread was created, the keep-alive queried every minute when set to 1, and SIGTERM ended it with `Shut down cleanly` and exit code 0 in 0.1 seconds.
- Compose: a thread created through the API got a sandbox container from `barrack-sandbox:dev` on the `barrack-sandboxes` network; a message sent through a client WebSocket was recorded and answered by the fake agent, and the run settled; after the control plane restarted, the thread's history replayed from Postgres and every supervisor reconnected. From inside a sandbox, as the agent's user: the control plane connected; `database` and `docker-api` did not resolve, their addresses timed out, the published port on the network's gateway was refused, and no Docker socket existed. Through the proxy, `docker ps` and `docker exec` were refused.

That run came before sign-in and acknowledged delivery were added. Since then Compose has been checked only to refuse to start without the sign-in settings (`docker compose config`); running it with a real Supabase project is still to do.

The socket proxy's rules were checked again on 2026-11-24, when the supervisor's token began to be handed over as a file: the proxy ran from its pinned image with exactly the flags in `compose.yaml` (only `-allowfrom` naming the test's client), and the Docker provider, run through it from that client, created a sandbox, put its token in with `docker cp -` (the CLI's `HEAD` and `PUT` of the container's archive), started, stopped and started it again with a replacement token, read a failed sandbox's log for its supervisor's words, and removed both; the token file held the replacement, owned by `barrack-supervisor`, mode 0400, in a 0700 directory, and `docker inspect` showed no token. `docker ps` and `docker exec` were still refused. The whole stack was not brought up, since its control plane needs a real Supabase project for sign-in.
