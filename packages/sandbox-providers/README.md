# Sandbox providers

`@barrack/sandbox-providers` is the boundary between the control plane and the computers threads run on. The control plane depends only on the `SandboxProvider` interface in [`src/sandbox-provider.ts`](src/sandbox-provider.ts): create a thread's sandbox, start it, stop it, destroy it, read its state, and get an address for a service inside it. Everything else happens through the supervisor inside the sandbox, which connects out to the control plane.

- **Providers hold no lifecycle policy.** The control plane decides when a sandbox runs. A provider guarantees that whenever a sandbox is running, its supervisor is running with the environment and secrets it was created with (or the secrets a later `start` replaced) and the sandbox's files intact.
- **Settings and secrets are different things.** A creation request carries `supervisorEnvironment`, plain settings the provider sets as the sandbox's environment, and `supervisorSecrets`, which it hands the supervisor's user alone, as one file per secret in the directory it names in `BARRACK_SUPERVISOR_SECRETS_DIRECTORY` ([`src/supervisor-secrets.ts`](src/supervisor-secrets.ts)), kept across a stop and a start. A secret is never in the sandbox's environment, so a process the provider's own command interface starts (`docker exec`, Daytona's) does not inherit it, whoever it runs as; nor in what the provider reports about the sandbox, a command's arguments, a log line or an error. The contract suite checks every provider for this. `start` may hand over `replacementSecrets`, which a creation taken over uses to give a sandbox an earlier attempt made its own token.
- **An identifier always means the same computer.** No operation creates or substitutes a sandbox other than the one named; a thread has at most one sandbox (`SandboxAlreadyExistsError` names it).
- **Sandboxes outlive the provider object.** A provider made afresh, as by a control plane started again, finds, stops and starts the sandboxes an earlier one created; the contract suite checks it.
- **Idempotent where it means something.** Starting a running sandbox, stopping a stopped one and destroying a missing one do nothing.
- **Typed failures.** `SandboxNotFoundError`, `SandboxProviderUnavailableError` (may pass; retry later), `SandboxRefusedError` (will not pass until something changes) and `SandboxAlreadyExistsError`. Messages never contain the supervisor's environment or secrets, and errors never carry a provider's own error object, which can hold credentials.
- **A failed operation leaves nothing half-done.** A create that fails part-way removes what it made, and a start whose supervisor cannot be launched stops the sandbox again, so nothing is left running, or billed, without a supervisor. If undoing fails too, the error is a `SandboxRefusedError` that keeps both explanations and names what was left behind, since retrying automatically would only find it.

## Providers

| Provider      | Folder                                   | What a sandbox is                                                                     |
| ------------- | ---------------------------------------- | ------------------------------------------------------------------------------------- |
| fake          | [`src/fake`](src/fake)                   | An in-memory record, for tests of the control plane                                   |
| docker        | [`src/docker`](src/docker)               | A container from the [sandbox image](../../sandbox-image), via the docker CLI         |
| daytona       | [`src/daytona`](src/daytona)             | A Daytona sandbox from a snapshot of the sandbox image                                |
| local-process | [`src/local-process`](src/local-process) | **Not a sandbox.** A directory and a child process on the control plane's own machine |

`readSandboxProviderConfiguration(process.env)` ([`src/provider-configuration.ts`](src/provider-configuration.ts)) reads the choice and `createSandboxProvider(configuration)` ([`src/create-sandbox-provider.ts`](src/create-sandbox-provider.ts)) builds it.

**What has run.** The fake and local-process providers run in every `pnpm test`, and the Docker provider against real containers in `pnpm test:docker`. The Daytona provider has run only against an in-memory stand-in for Daytona's API: it has never created a real Daytona sandbox.

| Variable                               | For           | Meaning                                                                                                        |
| -------------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------- |
| `BARRACK_SANDBOX_PROVIDER`             | all           | `docker`, `daytona`, `local-process` or `fake`                                                                 |
| `BARRACK_ALLOW_UNISOLATED_SANDBOXES`   | local-process | Must be exactly `development-only`, or the provider is refused                                                 |
| `BARRACK_LOCAL_SANDBOX_DIRECTORY`      | local-process | Absolute path; each sandbox gets a directory in it                                                             |
| `BARRACK_LOCAL_SUPERVISOR_COMMAND`     | local-process | JSON array: the supervisor's executable and arguments, e.g. `["node", "apps/sandbox-supervisor/dist/main.js"]` |
| `BARRACK_LOCAL_STOP_TIMEOUT_SECONDS`   | local-process | Grace period before a stopping supervisor is killed (default 15)                                               |
| `BARRACK_DOCKER_IMAGE`                 | docker        | The sandbox image, e.g. `barrack-sandbox:dev`                                                                  |
| `BARRACK_DOCKER_CPUS`                  | docker        | CPUs per sandbox (default 2)                                                                                   |
| `BARRACK_DOCKER_MEMORY_MEBIBYTES`      | docker        | Memory per sandbox, without swap (default 4096)                                                                |
| `BARRACK_DOCKER_PROCESS_LIMIT`         | docker        | Processes per sandbox (default 1024)                                                                           |
| `BARRACK_DOCKER_STOP_TIMEOUT_SECONDS`  | docker        | Grace period before a stopping supervisor is killed (default 15)                                               |
| `BARRACK_DOCKER_SERVICE_PORTS`         | docker        | Comma-separated ports `getServiceAddress` may hand out (default none)                                          |
| `BARRACK_DOCKER_EXECUTABLE`            | docker        | The docker command (default `docker`)                                                                          |
| `BARRACK_DOCKER_NETWORK`               | docker        | The Docker network sandboxes join (default: Docker's default bridge); see [compose.yaml](../../compose.yaml)   |
| `DAYTONA_API_KEY`                      | daytona       | Daytona API key, with exactly `write:sandboxes` and `delete:sandboxes`; never logged                           |
| `BARRACK_DAYTONA_SNAPSHOT`             | daytona       | The snapshot registered from the sandbox image                                                                 |
| `DAYTONA_TARGET`                       | daytona       | Region; the organisation's default when unset                                                                  |
| `BARRACK_DAYTONA_AUTO_ARCHIVE_MINUTES` | daytona       | Minutes after a stop before Daytona archives the sandbox (default 60)                                          |

**Docker.** One container per thread, named `barrack-thread-<thread>` and labelled `barrack.sandbox=true` and `barrack.thread-id=<thread>`; its identifier is the full container ID. The supervisor is the container's main process, and reaches a control plane on the host as `host.docker.internal`, or, with `BARRACK_DOCKER_NETWORK`, a control plane in a container on that network by its name there. Containers drop every capability except the two the image's `run-as-agent` needs to start the agent as another user, may write no core file (`--ulimit core=0`), are never privileged, and publish only the configured service ports, on `127.0.0.1`. `no-new-privileges` is not set, since it would stop `run-as-agent` receiving its capabilities; the helper sets `no_new_privs` on every process of the agent's instead. A sandbox is made in three steps: `docker container create`, with the supervisor's settings passed through the docker CLI's own environment, never its arguments; `docker container cp -`, which unpacks a tar archive read from standard input into `/var/lib/barrack/secrets`, one file per secret, owned by the supervisor's user (10001) and mode 0400, as the archive says, since `--archive` is not given; and `docker container start`. The secrets are in the container's own writable layer, so they survive a stop and a start, and are neither in an image layer nor in `docker inspect`; anyone who can `docker export`, `docker commit` or `docker exec` as the supervisor's user into the container can read them, as anyone with the daemon can read anything. A step that fails removes the container. `docker exec` runs as the supervisor's user unless given `--user barrack-agent`, which the agent's files need; as the agent it gets the container's environment, which holds no secret, and cannot open the secrets directory.

**Daytona.** Built on Daytona's generally available platform through the SDK's `v0` namespace. Auto-stop is off (it ignores an agent working inside the sandbox) and auto-delete is off; stopped sandboxes are archived after `BARRACK_DAYTONA_AUTO_ARCHIVE_MINUTES`, which stops disk billing and frees storage quota at the cost of a slower start. The sandbox's `envVars` hold the supervisor's settings and no secret. After a create, and after a start that replaces secrets, the provider uploads each secret into `/var/lib/barrack/secrets` (Daytona's file API) and sets it to the supervisor's user, mode 0400; then it runs the image's `barrack-ensure-supervisor`, after every create and start. A sandbox in which either fails is deleted after a create and stopped after a start. None of this has run against Daytona: which user its daemon writes files and runs commands as, and the rest a first run must check, are in the [first-deployment checklist](../../docs/deployment.md#first-deployment-checklist). Service addresses are signed preview URLs bound to one port with an expiry of at most a day, never the standard preview token, which opens every port.

**Local process: not a sandbox.** For `pnpm dev` and the fast cross-application tests only. Each thread's supervisor runs as an ordinary child of the control plane, as the same user, on the same machine, with **no isolation at all**: the agent can read and change everything that user can, including other threads' files and the control plane's environment. It is refused unless `BARRACK_ALLOW_UNISOLATED_SANDBOXES=development-only` is set, and the control plane also refuses it unless it listens on the loopback interface. Each sandbox is a directory `<BARRACK_LOCAL_SANDBOX_DIRECTORY>/local-<uuid>/` holding `workspace/` (made a Git repository of its own, so the agent's Git commands never reach a checkout it happens to sit in), `state/`, `supervisor/` and `secrets/` (0700, a 0600 file per secret, which keeps them out of the supervisor's environment and from the machine's other users, but not from the agent, which runs as the same user); the supervisor runs in `workspace/` with `BARRACK_WORKSPACE_DIRECTORY`, `BARRACK_STATE_DIRECTORY` and `BARRACK_SUPERVISOR_STATE_DIRECTORY` pointing at them, plus a few basics from the host (`PATH`, `HOME`, locale, proxy settings) and the requested environment, which overrides them. **Stop keeps the files** in the sense that stopping ends the supervisor and leaves the directory on disk, and starting launches the supervisor again in it. What the provider knows of a sandbox is kept in its directory (`sandbox-record.json`, readable by its owner only, and `supervisor.pid` while the supervisor runs, renamed `supervisor-stopping.pid` before it is signalled so a stop cut short is finished by the next), so a control plane started again finds every earlier sandbox: a supervisor that outlived a control plane killed outright is reported running and can be stopped, and a stopped one can be started again. A control plane that exits normally asks every supervisor it started to stop. A supervisor that exits by itself leaves its sandbox `failed`. Service addresses are plain `http://127.0.0.1:<port>/` on the host. Supervisor output goes to the control plane's own standard output.

## Tests

`pnpm test` runs the unit tests and the contract suite ([`src/test-support/sandbox-provider-contract.ts`](src/test-support/sandbox-provider-contract.ts)) against the fake and the local-process provider (with a small stand-in supervisor, [`src/test-support/stand-in-supervisor.ts`](src/test-support/stand-in-supervisor.ts)). The contract runs against real containers with `pnpm test:docker`, and against Daytona only when `DAYTONA_API_KEY` and `BARRACK_DAYTONA_SNAPSHOT` are set; otherwise those suites are skipped with the reason in their name.
