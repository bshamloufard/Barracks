# @barrack/control-plane

The service between thread sandboxes and clients. It creates threads: each new thread gets a sandbox of its own from the configured [sandbox provider](../../packages/sandbox-providers), whose supervisor is given a token minted for that thread alone. Each thread's supervisor then connects to the control plane over a WebSocket, and so does each client viewing the thread. The control plane records every agent event in the thread's ordered history before showing it to anyone, relays streamed text live, and passes the user's messages and interrupts to the supervisor. Delivery between supervisor and control plane is acknowledged both ways, so each agent event is recorded exactly once and each user message reaches the agent exactly once, in order, even across either side being killed (see [the architecture](../../docs/architecture.md#acknowledged-delivery)).

Users sign in with Supabase Auth, and the control plane verifies every access token itself: each user sees and controls only their own threads (see [Signing users in](#signing-users-in)). With Supabase authentication it may listen on any address. In development mode (`BARRACK_AUTHENTICATION=development-single-user`, which `pnpm dev` uses) there is no sign-in and every client is one fixed user, so it refuses to listen anywhere but a loopback address, and answers only requests and WebSocket upgrades addressed to `localhost`, `127.0.0.1` or `[::1]` (any port), on every path, with `403 forbidden_host`. Listening on loopback keeps other machines out, but a website you visit can point its own domain at 127.0.0.1 (DNS rebinding) and then read whatever the control plane answers it, since its requests count as same-origin and carry no `Origin` header; its `Host` header still names its domain, which is why that is checked. The check also refuses anything reaching a development control plane through a proxy that keeps the original `Host`. With Supabase, other websites cannot act through your browser because the access token is never sent automatically, as a cookie would be; the control plane also refuses browser requests from an `Origin` it does not serve the client from.

> **Not yet ready for strangers.** Sign-in is in place. One deployment runs on Railway against a real Supabase project (it migrated the database and read the project's signing key), but nobody has signed in to it, and none of this has run against Daytona, a real GitHub App or a real model provider (see the [first-deployment checklist](../../docs/deployment.md#first-deployment-checklist)). For providers the model proxy does not relay, each user's own key is placed in their threads' sandboxes (see below). Admit only people you trust.

Threads and their history are stored in Postgres when `BARRACK_DATABASE_URL` is set, and survive restarts. Without it, they are kept in memory and lost when the process stops, which suits local development only; the control plane says so in a warning at startup.

## Threads and their sandboxes

1. `POST /api/threads` mints a thread identifier (a UUID) and a supervisor token (32 random bytes), records the thread with the token's SHA-256 digest and its sandbox `creating`, if the user has a place under the limit on running sandboxes, and answers `201` at once.
2. In the background it asks the provider to create the sandbox, with the supervisor's plain settings as its environment, `BARRACK_CONTROL_PLANE_URL` (from `BARRACK_SANDBOX_CONTROL_PLANE_URL`), `BARRACK_THREAD_ID`, `BARRACK_AGENT_HARNESS`, and for Pi the Pi settings described below; and the token as its one secret, `BARRACK_SUPERVISOR_TOKEN`, which the provider hands the supervisor's user alone as a file, never in the sandbox's environment (see [the providers' README](../../packages/sandbox-providers/README.md)). No model and no model key: the thread's model and its owner's key reach the supervisor over its connection (see [Model access](#model-access)). The token goes nowhere else: it is never stored, logged or returned.
3. When the provider answers, the thread's sandbox is recorded `running`; if it refuses, or stays unavailable after two more tries (1 s and 5 s later), it is recorded `failed` with a reason the user is shown. A provider that reports the sandbox already exists on a retry is taken to have created it on the earlier attempt.
4. The supervisor connects to `/threads/{threadId}/supervisor` with `Authorization: Bearer <token>`. The upgrade is accepted only with a token minted for that thread's creation, compared by digest in constant time; another thread's valid token gets `401`. Clients can connect only to their own threads, after authenticating (see [Signing users in](#signing-users-in)).

### The sandbox's lifecycle

The control plane decides when each thread's sandbox runs ([`src/sandbox-lifecycle/`](src/sandbox-lifecycle)); providers hold no policy. Every thread records its sandbox as `creating`, `running`, `stopping`, `stopped`, `starting`, `failed` (with a reason, and resumable if the sandbox still exists) or `deleting`, and changes it only by a conditional update on the version it read, so of two requests or two control planes acting at once exactly one succeeds. The [architecture](../../docs/architecture.md#a-threads-sandbox-lifecycle) gives every state and rule; in short:

- **Stop** (`POST /api/threads/{threadId}/stop`) interrupts the agent, waits up to 5 s for its run to end, and stops the sandbox with its files kept. **Resume** (`POST /api/threads/{threadId}/resume`) starts it again, and Pi reopens its session. **Delete** (`DELETE /api/threads/{threadId}`) destroys the sandbox, then removes the thread's history and record for good.
- **A message to a stopped sandbox** wakes it, and waits in history until the agent is back.
- **Idle shutdown**: a running sandbox is stopped after `BARRACK_SANDBOX_IDLE_MINUTES` with no user message, agent event, publication under way or input from a user holding the desktop, counted from its supervisor's first attachment, while its agent has no run open and no message waiting. A client merely watching does not count.
- **The limit**: creating, resuming or waking a sandbox is refused (`409 sandbox_limit_reached`, or a rejected message, naming the user's sandboxes that take a place) when the user already has `BARRACK_RUNNING_SANDBOXES_PER_USER` sandboxes creating, running, starting or stopping, or being deleted while they still have one, or the installation `BARRACK_RUNNING_SANDBOXES_IN_TOTAL`.
- **Reconciliation**, at startup and every `BARRACK_SANDBOX_CHECK_SECONDS`: an operation whose control plane was killed is taken over once its lease (twice that interval) lapses; each running sandbox is compared with what the provider reports; and one whose supervisor has not attached within five minutes is stopped and its thread failed, naming `BARRACK_SANDBOX_CONTROL_PLANE_URL`.
- **A provider that fails** part way leaves the state the provider then reports, with a reason the user is shown (`problem` on a running or stopped sandbox, `reason` on a failed one).

A client learns all this from the thread's `sandbox` field (`GET /api/threads/{threadId}`); whether the agent is reachable right now it learns from the thread's WebSocket.

### Repositories and GitHub

A thread may start from one repository ([`src/repositories/`](src/repositories)): a public one, cloned without credentials, or one of the user's repositories through the installation's GitHub App ([`src/github/`](src/github)), which they link in the web client's Settings. The control plane records it with the thread, tells the supervisor what to clone right after its welcome, answers the sandbox's requests for read-only credentials for that one repository, and publishes the thread's branch itself ([`src/publication/`](src/publication)), checking the sandbox's bundle as hostile input and pushing only to `barrack/<thread id>`. Everything about it is in the [architecture](../../docs/architecture.md#working-with-a-git-repository); setting up the App is in the [deployment guide](../../docs/deployment.md#4-github-optional-private-repositories-and-pull-requests). Publishing needs `git` on the control plane's path, which its image carries.

### Model access

Each user adds their own key per model provider, and each thread runs on a model its owner chose, on its owner's key ([`src/model-access/`](src/model-access)); the control plane forwards no key of its own. Keys are sealed with AES-256-GCM under `BARRACK_MODEL_CREDENTIAL_KEY`, bound to their owner and provider, in `model_credentials` or in memory; no answer, log line or event holds one. After each supervisor's welcome, and whenever the key or the model changes, the thread's relay sends `configure_model_access` with the thread's model and its owner's key for that model's provider, decided from the thread's record alone. A user message to a thread whose owner has no such key is refused, saying which key to add and where. At startup the control plane refuses to run if a stored key was sealed under a key it was not given, and seals again under the current key what a previous one sealed, at startup and every five minutes. The providers and models offered come from [`@barrack/model-catalogue`](../../packages/model-catalogue). Everything about it is in the [architecture](../../docs/architecture.md#each-users-own-model-access) and the [deployment guide](../../docs/deployment.md#users-model-keys-and-the-key-that-seals-them).

For the providers the catalogue package lists as relayed, the key stays here: the supervisor is told a token for the model proxy instead (`src/model-proxy/`), which agents reach at `/threads/{threadId}/model-proxy/{providerId}/…`, routed before the HTTP app (`src/http/route-http-request.ts`). The proxy checks each request's token, thread, owner and cap against the records, relays only requests shaped like the pinned agent's (running offline with its built-in model catalogue, as the supervisor runs it: the top level's members and settings, those of the conversation items that carry settings, and the types of everything else the format gives a meaning to), forwards it to the provider's own address with the owner's key, streams the answer back and measures its usage (`src/model-usage/`), which also keeps what sandboxes report for other providers and each user's own cap. See the [architecture](../../docs/architecture.md#the-model-proxy), and [what the cap is](../../docs/architecture.md#what-the-cap-is).

A user may instead run their OpenAI models on their ChatGPT plan, where the operator turns it on (`BARRACK_CHATGPT_PLAN_SIGN_IN=on`, refused unless the installation admits one user) ([`src/chatgpt-plan/`](src/chatgpt-plan)). The control plane signs the user in at OpenAI itself (PKCE, `state`, an OpenID nonce, the issued client reused, the ID token validated) from the address the user's browser ends on, which they paste back; keeps the plan's tokens sealed like keys; renews the access token under a lock on the user's sign-in row, writing the rotated refresh token in the same transaction; and revokes it on disconnect. The proxy spends the plan's access token in place of a key, and relays only requests shaped as the pinned agent sends OpenAI's programme. See the [architecture](../../docs/architecture.md#a-users-chatgpt-plan) and the [deployment guide](../../docs/deployment.md#chatgpt-plans).

### Pi's settings

A control plane running Pi also forwards one of Pi's own settings from its environment to every sandbox, when set: `PI_CACHE_RETENTION` (`long` for extended prompt caching). The list is in [`src/threads/pi-settings.ts`](src/threads/pi-settings.ts); other `PI_` variables are not forwarded. `PI_OFFLINE` is not a setting: the supervisor always runs Pi offline, so that it keeps to its built-in model catalogue, which is what the model proxy's list of the agent's requests describes ([what the cap is](../../docs/architecture.md#what-the-cap-is)).

## The HTTP API

JSON in and out, with shapes defined in [`@barrack/protocol`](../../packages/protocol/src/threads-api.ts). Errors answer `{ "error": { "code": "...", "message": "..." } }`.

Every `/api` request but the client configuration needs `Authorization: Bearer <access token>`: without a valid one it answers `401 unauthorized`, and for a signed-in user the installation does not admit, `403 not_allowed`. A browser request whose `Origin` is not allowed answers `403 forbidden_origin`; one without `Origin` (a native app) is let through to authenticate. Requests see only the signed-in user's threads: another user's thread answers `404` exactly as a missing one does.

| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Public.                                                                                                                                                                      |

Needs `Content-Type: application/json` (`415`). |
| `POST /api/threads` with `{ "repository": … }`                            | The same, starting from `{ "url", "access", "baseBranch"? }`, where `access` is `"none"` (a public repository) or `"github_app"`; `400` for a URL refused, `403 repository_not_allowed`.                                                                                                       |
| `GET /api/threads`                                                        | `200 { "threads": [Thread, …] }`, the user's own, the most recently active first, at most 100.                                                                                                                                                                                                 |

| `GET /api/chatgpt-plan`                                                   | `200`: whether ChatGPT plans are offered here, the user's connected plan (when, and the account's email), a plan lost (why, when), and what their OpenAI models run on ([`chatgpt-plan.ts`](../../packages/protocol/src/chatgpt-plan.ts)).                                                     |
| `POST /api/chatgpt-plan/sign-in` with `{ "allowsBackgroundUse": true }`   | `200 { "authorizationUrl", "expiresAt" }`: OpenAI's page to open; `409 chatgpt_plan_unavailable` where plans are not offered.                                                                                                                                                                  |
| `POST /api/chatgpt-plan/sign-in/completion` with `{ "finalAddress" }`     | `200` with the status, connected; `400 chatgpt_sign_in_failed` saying what is wrong with the address (not one, cut short, OpenAI's own page, another sign-in's, used, lapsed) or what OpenAI refused.                                                                                          |

A `Thread` is `{ "threadId", "createdAt", "lastActiveAt", "title" (from the first message, or null), "isAgentWorking", "sandbox": { "state": … }, "repository": { "url", "access", "baseBranch", "workBranch", "publishing" } or null, "model" (`provider/model`, or null) }`, as [`threads-api.ts`](../../packages/protocol/src/threads-api.ts) defines. When the store cannot be reached, requests answer `503`.

Outside `/api`, `PUT /threads/{threadId}/supervisor/publication-bundles/{publicationId}` takes a publication bundle from the thread's supervisor, with its token, and only while that publication waits for it.

## Signing users in

**Over HTTP**, each request carries the access token. **Over the client WebSocket**, `/threads/{threadId}/client`, the first message must be `{ "type": "authenticate", "accessToken": "…" }`, within 5 seconds; anything else closes the connection with `notAuthenticated` (4401), and nothing in time with `authenticationTimedOut` (4405), which a client retries rather than asking the user to sign in again, having sent nothing. The control plane then checks that the user owns the thread (`threadNotFound`, 4404, if not, the same as for a missing thread) and only then replays, sends the thread's current statuses (whether its supervisor is connected, and how far user messages have been delivered) and goes live. The client sends each refreshed token on the open connection; one for another user closes it (4401), and when the newest expires it closes with `accessTokenExpired` (4402), after which the client refreshes its token and reconnects from its last seen sequence. A user the installation does not admit is closed with `userNotAllowed` (4403).

**Over the desktop viewer's WebSocket**, `/threads/{threadId}/desktop`, the same rules hold, codes included, through the same code ([`websocket/connection-authentication.ts`](src/websocket/connection-authentication.ts)): its `Origin` must be allowed, its first message is `authenticate`, another user's thread is answered as a missing one, and an expired token closes it. A viewer is then told the desktop is ready, or why not (`desktop_unavailable`, then `desktopUnavailable`, 4410; a stopped sandbox is never woken for it), and is closed with `desktopStreamEnded` (4411) when the sandbox's side of its stream ends. A supervisor's desktop stream, `/threads/{threadId}/desktop-streams/{streamId}`, is accepted only with the thread's token and only for a stream identifier minted for that thread, once; anything else gets `401`. What each viewer may send, and the bounds on both directions, are in [the architecture](../../docs/architecture.md#the-live-desktop).

Tokens are verified against the Supabase project's published public keys (issuer, audience `authenticated`, ES256 or RS256, expiry with 30 seconds' tolerance, a signed-in, non-anonymous user). The user is the token's `sub`, recorded in `barrack.users` on their first authenticated request. An address on `BARRACK_ALLOWED_USER_EMAILS` counts only once Supabase confirms the user owns it, which the control plane asks Supabase once per user.

**What a self-hoster sets up in Supabase** (asymmetric signing keys, the installation's address as the Site URL and on the Redirect URLs, where sign-in links return, custom SMTP for anyone outside the project's organisation, a code in the email if wanted, sign-ups off once listed users exist, and the publishable key, never the secret key) is in the [deployment guide](../../docs/deployment.md#1b-supabase-sign-in). A sign-in link returns to `/?code=…`, which the control plane serves like any other visit to `/`: the web client exchanges the code with Supabase itself, and the control plane never sees a token until the client sends one. At startup the control plane does not listen until it has read the project's published keys, retrying for as long as Supabase cannot be reached, and refuses to start if the project publishes no asymmetric key.

Threads created before sign-in existed have no owner and are shown to nobody; give one an owner with `update barrack.threads set owner_user_id = '<user id>' where thread_id = '<thread id>';` once that user has signed in.

## Browser security headers

Every answer of the HTTP app carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: same-origin` ([`src/http/security-headers.ts`](src/http/security-headers.ts)). The built web client's files, the page and its assets, carry a Content-Security-Policy worked out from what the client does ([`src/http/web-client-content-security-policy.ts`](src/http/web-client-content-security-policy.ts)); for `https://<domain>` signing in with `https://<ref>.supabase.co`:

```
default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self' wss://<domain> https://<ref>.supabase.co; base-uri 'none'; form-action 'self'; frame-ancestors 'none'
```

`connect-src` lists the WebSocket form of each origin in `BARRACK_ALLOWED_CLIENT_ORIGINS` and the origin of `BARRACK_SUPABASE_URL` (none in development mode); `data:` images are how noVNC draws the desktop's JPEG rectangles and its cursor. API answers, `/health` and refusals carry `default-src 'none'; frame-ancestors 'none'` instead. `Strict-Transport-Security: max-age=31536000` is sent only when the proxy in front says the browser came over HTTPS (`X-Forwarded-Proto: https`, which Railway's edge sets) and the `Host` is not a loopback name, so `http://localhost` installations, `pnpm dev` and Railway's health check never get it. In `pnpm dev` the page is Vite's, which sends none of the page's headers; Vite's development page needs inline scripts the policy would refuse. An end-to-end test runs the built client under the policy in Chromium ([`web-client-security-policy.test.ts`](../../tests/end-to-end/src/web-client-security-policy.test.ts)).

| `src/chatgpt-plan/`           | Users' ChatGPT plans: the operator's setting, signing in at OpenAI from the pasted address, the sealed sign-in and its stores, renewing it one at a time, revoking it, and the plan's models.      |

| `src/model-usage/`            | Each user's model usage per thread, model, source and hour, their own cap, and whether a cap is reached.                                                                                           |
| `src/publication/`            | Publishing a thread's branch: the bundle upload, checking it as hostile input, the push and the pull request.                                                                                      |
| `src/storage/`                | Opens Postgres (migrated) or memory for the thread store and the event log.                                                                                                                        |
| `src/database/`               | Database settings, the connection pool, the migration runner, and waiting for the database at startup (`pg`).                                                                                      |
| `migrations/`                 | The SQL migrations, applied in name order.                                                                                                                                                         |
| `src/thread-event-log/`       | The `ThreadEventLog` interface, which assigns sequences, with its Postgres and in-memory implementations.                                                                                          |
| `src/thread-relay/`           | `ThreadRelay` and its parts: the queue, the clients' replay and fan-out, supervisor attachment and acknowledged delivery, in-progress text. No sockets here.                                       |
| `src/websocket/`              | Upgrade routing, per-thread supervisor tokens, each client's and desktop viewer's session (authentication, ownership, expiry), desktop streams, frame validation, heartbeats, slow clients (`ws`). |
| `src/test-support/`           | Fake peers and connections, a pausable event log, the store and log contract suites, test database helpers. Not built.                                                                             |

The endpoints and messages are defined in [`@barrack/protocol`](../../packages/protocol); see [docs/architecture.md](../../docs/architecture.md) for how they fit together.

## The database

Postgres 16 and 17 are tested; CI uses 17, which Supabase runs. The control plane keeps its tables in a schema of its own, `barrack`, creating it if needed, so the database role it connects as needs permission to create a schema (the owner of the database has it).

### Supabase

- **Connect through the session pooler**, on port 5432: the _Session pooler_ string in the project's **Connect** panel, which looks like `postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres`. The direct connection (`db.<project-ref>.supabase.co`) is IPv6 only, and Railway services have no outbound IPv6 unless it is turned on. The transaction pooler (port 6543) does not keep a session per client, which breaks the advisory lock migrations rely on, and prepared statements.
- **Trust Supabase's certificate authority.** Supabase signs its database certificates with its own authority, so verification fails without it. Download it under **Database settings → SSL configuration** and put the file's contents in `BARRACK_DATABASE_CA_CERTIFICATE` (Railway accepts multi-line values). Leave `BARRACK_DATABASE_TLS` at `verify-full`. If the certificate cannot be verified, the control plane refuses to start and says which variable to set.
- **Pool size.** The session pooler serves at most the project's _Pool Size_ connections (15 by default) per database role, shared with everything else using that role. The default of 5 leaves room for a second control plane during a redeploy, and for you.
- **Free projects pause** after a week without enough database activity, and an idle control plane queries the database only when a thread is used. So it also reads one row from `barrack.schema_migrations` every `BARRACK_DATABASE_KEEP_ALIVE_MINUTES` (four hours by default, after each previous query has finished), which keeps a project in use for Barrack from being paused. A failed query is logged and tried again at the next interval; the keep-alive stops before the pool closes at shutdown. Supabase does not define how much activity is enough; see [`src/database/database-keep-alive.ts`](src/database/database-keep-alive.ts).

The tables are not exposed through Supabase's Data API: it serves only the schemas you list as exposed, and every table has row level security turned on with no policies, so even an exposed schema would yield no rows to the `anon` or `authenticated` roles. See the comment at the top of [the first migration](migrations/0001_create_thread_event_log.sql).

### Other Postgres

- With a certificate from a public authority, set only `BARRACK_DATABASE_URL`.
- With a private authority, also set `BARRACK_DATABASE_CA_CERTIFICATE` to its certificate, for example `BARRACK_DATABASE_CA_CERTIFICATE="$(cat root.crt)"`.
- A database without TLS on the same machine or a private network (a local Docker container, say) needs `BARRACK_DATABASE_TLS=disable`; the control plane warns at startup that the connection is unencrypted. Never use it across the internet.

### Migrations

Migrations are plain SQL files in [`migrations/`](migrations), named `NNNN_description.sql` and applied in name order, each in its own transaction, with unqualified names created in the `barrack` schema. The control plane applies any pending ones at startup, before it accepts connections, so deploying a new version is all it takes; `pnpm --filter @barrack/control-plane migrate` applies them without starting the server (after `pnpm build`, with the same database variables).

- Applied migrations are recorded, with a checksum, in `barrack.schema_migrations`. **Never edit a migration that has been applied anywhere**: the control plane refuses to start if an applied file has changed, or if the database has a migration this build lacks (as after rolling back to an older version). Put every change in a new file.
- Two instances starting at once take turns under a Postgres advisory lock, so each migration runs once.

#### Migrations written in parallel

`0010` (acknowledged delivery) and `0020` (users and thread owners) were written on separate branches and merged together; each works on a fresh database in numeric order. A database migrated by the sign-in branch before that merge has `0020` applied without `0010`, and the control plane refuses to start on it, naming both. Only development and test databases can be in that state. Either drop its schema, losing its threads, and let the control plane migrate it afresh:

```sh
psql "$BARRACK_DATABASE_URL" --command 'drop schema barrack cascade'
```

or keep its threads by applying `0010` by hand and recording it as the control plane would, from the repository root:

```sh
migration=apps/control-plane/migrations/0010_acknowledge_supervisor_delivery.sql
psql "$BARRACK_DATABASE_URL" --single-transaction --set ON_ERROR_STOP=1 \
  --command 'set local search_path to barrack' \
  --file "$migration" \
  --command "insert into barrack.schema_migrations (name, checksum) values ('$(basename "$migration")', '$(sha256sum "$migration" | cut -d ' ' -f 1)')"
```

The two migrations touch different tables, so applying `0010` after `0020` leaves the same schema as applying them in order. A database migrated by the acknowledged-delivery branch needs nothing: it gains `0020` at the next start.

### When the database is unavailable

- At startup the control plane waits for the database, retrying with growing delays up to 30 seconds and logging each failure, and does not listen until it has migrated. A deployment that cannot reach its database therefore fails its health check instead of restarting in a loop. Errors that waiting cannot fix, such as a wrong password, an unverifiable certificate or a failing migration, stop it with a message.
- While running, a query waits at most 10 seconds for a connection and 30 seconds for an answer. An event that cannot be recorded disconnects its supervisor, which reconnects and sends it again; a client whose history cannot be read is disconnected, and reconnects. Nothing crashes, and once the database answers again everything carries on.
- `GET /health` reports only that the process is up. A separate readiness check is not needed, because the server does not listen until the database is migrated, and Railway consults the health check only while a deployment starts.

## Running it

`pnpm dev` at the repository root runs it in development mode with the web client and the local-process provider. With Docker sandboxes the control plane must listen on Docker's bridge address, which the agents can reach too, so development mode is refused there and you need a Supabase project, set up as in the [deployment guide](../../docs/deployment.md#1b-supabase-sign-in). From the repository root, after `pnpm install` and `pnpm sandbox-image:build`:

```sh
export BARRACK_SUPABASE_URL=https://<project-ref>.supabase.co BARRACK_SUPABASE_PUBLISHABLE_KEY=sb_publishable_…
export BARRACK_ALLOWED_USER_EMAILS=you@example.com
export BARRACK_SANDBOX_PROVIDER=docker BARRACK_DOCKER_IMAGE=barrack-sandbox:dev
export BARRACK_AGENT_HARNESS=fake
export BARRACK_MODEL_CREDENTIAL_KEY="$(openssl rand -base64 32)"   # keep it to keep users' keys
# Containers reach the host through Docker's bridge, so listen on its gateway address
# (reachable from this machine and its containers only, never 0.0.0.0).
export BARRACK_CONTROL_PLANE_HOST="$(docker network inspect bridge --format '{{(index .IPAM.Config 0).Gateway}}')"
export BARRACK_SANDBOX_CONTROL_PLANE_URL=ws://host.docker.internal:8787

# Development: restarts on every change.
pnpm --filter @barrack/control-plane dev

# Built: compile once, then run, also serving the built web client.
pnpm build
BARRACK_WEB_CLIENT_DIRECTORY="$PWD/apps/web/dist" pnpm --filter @barrack/control-plane start
```

The built client is then at `http://<that address>:8787/` (add it to `BARRACK_ALLOWED_CLIENT_ORIGINS`). `pnpm --filter` runs scripts inside `apps/control-plane`, so give `BARRACK_WEB_CLIENT_DIRECTORY` as an absolute path.

To keep history across restarts locally, start the throwaway test database (below) and add `BARRACK_DATABASE_URL=postgres://barrack:barrack@127.0.0.1:54329/barrack_test BARRACK_DATABASE_TLS=disable`.

Logs are JSON lines on standard output. Every line about a thread carries its `threadId`; pipe through `pino-pretty` if you want them readable.

## Tests

`pnpm test` at the repository root runs them. They start a real control plane on an ephemeral port with the fake sandbox provider, create threads through the API, and drive them with real WebSocket connections from a fake supervisor (holding the token the provider was given) and test clients. Most run as development mode's user; the tests of sign-in and access control (`src/access-control.test.ts`, `src/authentication/`) verify real tokens from a test identity issuer ([`tests/test-identity-issuer`](../../tests/test-identity-issuer)), which serves a key set on localhost as Supabase does, so no Supabase project is needed.

The tests of the Postgres thread store, the Postgres event log and the migration runner need a real database. Without one they are skipped, and their names say why. To run them:

```sh
pnpm test-database:start   # Postgres 17 in Docker on 127.0.0.1:54329, data in memory
export BARRACK_TEST_DATABASE_URL=postgres://barrack:barrack@127.0.0.1:54329/barrack_test
pnpm test
pnpm test-database:stop    # removes the container and its data
```

Each test works in a schema of its own with a random name and drops it afterwards, so any database you can create schemas in will do. TLS is off for the test database unless `BARRACK_TEST_DATABASE_TLS=verify-full` (with `BARRACK_TEST_DATABASE_CA_CERTIFICATE` if needed). CI always runs them, against a Postgres service container.
