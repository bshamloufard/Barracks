# Sandbox supervisor

A small long-running Node process that lives inside a thread's sandbox: a container from the [sandbox image](../../sandbox-image), or under `pnpm dev` an ordinary process on the developer's machine. It:

1. starts the coding agent ([Pi](https://github.com/earendil-works/pi), or a scripted fake);
2. dials **out** to the control plane over a WebSocket, so the sandbox needs no inbound networking;
3. translates what the agent does into Barrack's protocol (`@barrack/protocol`) and sends it;
4. carries out what the control plane asks: deliver a user message (each exactly once), interrupt the agent, and run on the thread's model with its owner's key (see [Model access](#model-access));
5. prepares the agent's workspace: clones the thread's repository, as the agent, before the agent is given anything, answers Git's requests for read-only credentials by asking the control plane, and bundles the work branch's commits when the control plane publishes them (see [Working with a repository](#working-with-a-repository)).
6. keeps the sandbox's desktop running, opens a desktop stream to it whenever the control plane asks, and gives the agent a computer tool that stands back while the user holds the desktop (see [The desktop and computer use](#the-desktop-and-computer-use)).

## Configuration

Everything comes from environment variables, checked at startup. Every problem is listed at once, and values are never echoed. The control plane sets them when it creates the thread's sandbox (see [its README](../control-plane/README.md#threads-and-their-sandboxes)), and the sandbox image sets the directories and the agent's user.

| Variable                               | Required       | Meaning                                                                                                                                                                                                          |
| -------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BARRACK_CONTROL_PLANE_URL`            | yes            | WebSocket base URL of the control plane, e.g. `ws://127.0.0.1:8787`                                                                                                                                              |
| `BARRACK_THREAD_ID`                    | yes            | The thread this sandbox belongs to                                                                                                                                                                               |
| `BARRACK_SUPERVISOR_TOKEN`             | yes            | This thread's own token, sent as `Authorization: Bearer …`. Never logged; see below for who can read it                                                                                                          |
| `BARRACK_SUPERVISOR_STATE_DIRECTORY`   | yes            | What the supervisor keeps across its own restarts; only its user should be able to write here                                                                                                                    |
| `BARRACK_AGENT_HARNESS`                | no             | `pi` (default) or `fake`                                                                                                                                                                                         |
| `BARRACK_WORKSPACE_DIRECTORY`          | for `pi`       | The agent's working directory, where the thread's repository is cloned; optional for `fake`                                                                                                                      |
| `BARRACK_GIT_HELPER_SOCKET`            | no             | The Unix socket Git's credential helper asks the supervisor on; must be reachable by the agent and nobody outside the sandbox. Default: `git-credential.sock` in the state directory                             |
| `BARRACK_STATE_DIRECTORY`              | for `pi`       | Pi's sessions (`pi/sessions`) and agent directory (`pi/agent`: credentials, settings, models)                                                                                                                    |
| `BARRACK_AGENT_USER`                   | for `pi`       | The operating-system user Pi runs as, other than the supervisor's; see below                                                                                                                                     |
| `BARRACK_AGENT_SHARES_SUPERVISOR_USER` | no             | Exactly `development-only` lets Pi run as the supervisor's own user; see below                                                                                                                                   |
| `BARRACK_LOG_LEVEL`                    | no             | `debug`, `info` (default), `warn` or `error`                                                                                                                                                                     |
| `BARRACK_DESKTOP_COMMAND`              | no             | A program that runs the sandbox's desktop in the foreground until its standard input closes (the image's `barrack-desktop`). Unset: the sandbox has no desktop; see [the desktop](#the-desktop-and-computer-use) |
| `DISPLAY`                              | with a desktop | The desktop's X display, such as `:1`; given to Pi only when the sandbox has a desktop                                                                                                                           |
| `BARRACK_DESKTOP_VNC_PORT`             | no             | The loopback port of the desktop's VNC server; default `5900`                                                                                                                                                    |
| `BARRACK_DESKTOP_CONTROL_FILE`         | no             | Where the supervisor writes who holds the desktop's input, for the computer tool; the agent must be able to read it and not write it. Default: `desktop-control` in the state directory                          |

Pi gets an environment built from an allowlist (see [`src/pi/pi-environment.ts`](src/pi/pi-environment.ts)): basics such as `PATH` and `HOME`, proxy settings and every `PI_*` variable. Model provider keys (`ANTHROPIC_API_KEY` and the like) and ambient cloud credentials (`AWS_*`, `GOOGLE_*`) are deliberately not passed: neither the model nor its key is configured here.

## Model access

The thread's model and what reaches its provider arrive from the control plane, never from the environment: `configure_model_access`, right after `prepare_workspace` and again whenever either changes, carried out in the same queue as user messages, so a message never reaches the agent before its credential. The credential is one of two kinds: for a provider the control plane relays, a `proxy_token` (a token for the control plane's model proxy, worth nothing anywhere else, and the proxy's address for this thread and provider); for any other, an `api_key`, the owner's key itself.

- **Where it goes.** The Pi harness writes it to Pi's own credential file, `auth.json` in `pi/agent`, as the agent's user, and for a proxy token also sets that provider's `baseUrl` in Pi's `models.json` to the proxy's address, leaving the rest of that file as it is: a short Node program run through the agent launcher reads what to write from its standard input and renames new files over the old ([`src/pi/pi-credential-file.ts`](src/pi/pi-credential-file.ts)). Pi rereads `auth.json` whenever it changes, so a replaced credential is used from Pi's next request with no restart; it reads `models.json` when it starts. The files are erased (and the proxy's addresses removed) when the supervisor starts (one killed earlier may have left them), when the credential is withdrawn, and when the supervisor stops. Neither is in any process's environment, so nothing started in the sandbox through `docker exec` or a provider's command interface inherits it, and the agent's commands do not print it with `env`.
- **What the agent can do with it.** Pi runs as the files' owner, so the agent can read what it was given, and so can any code a repository makes it run: a key placed here can be sent anywhere, a proxy token is useless outside its own thread's proxy; see the sandbox image's README.
- **A model switch during a run** takes effect for the next run: until the run in progress ends, `auth.json` keeps the running model's provider's credential beside the new model's, then Pi starts again on the new model with the new credential alone ([`src/pi/pi-credential-plan.ts`](src/pi/pi-credential-plan.ts)).
- **When Pi runs.** Only with a model and a credential: it starts once the first key arrives; with the key withdrawn it is stopped once its run ends, and a message is answered, without Pi, by an errored message saying a key is needed (`errorKind: "credential_missing"`); on another model it is started again once the run in progress ends, resuming its session, so the new model is sent the conversation so far (the pinned Pi cannot switch to a provider that had no key when it started).
- **Failures.** A provider's refusal is classified from Pi's error report ([`src/pi/classify-model-access-error.ts`](src/pi/classify-model-access-error.ts)) into `credential_rejected`, `quota_exhausted` or `rate_limited`, the last only once Pi's own retries have run out, and the model proxy's refusal for a reached cap into `usage_cap_reached`, carried as the errored assistant message's `errorKind`.
- **Usage.** Each assistant message carries what Pi says producing it used (`usage`), which the control plane counts as reported usage for providers it does not relay, and ignores for those it does, since it measures them itself.
- **Never logged or sent.** The supervisor remembers every key it is given and replaces it with `[redacted model credential]` wherever it turns up in an agent event, a stream fragment or a log line ([`src/secret-redactor.ts`](src/secret-redactor.ts)): a safety net against a provider echoing a key or a tool printing the file, not a boundary against an agent that means to send it.

### Which user the agent runs as

Leaving the token out of Pi's environment stops it from turning up in something Pi prints or sends to the model by accident. Keeping it from a determined agent takes a different operating-system user, because Linux shows a process's environment (`/proc/<pid>/environ`), memory and file descriptors, and lets it be signalled or traced, only by processes of the same user.

How Pi is started is decided in one place, [`src/agent-process`](src/agent-process), so the Pi harness has no idea which user it runs as:

- **Same user**, only when chosen by name with `BARRACK_AGENT_SHARES_SUPERVISOR_USER=development-only` (the local-process provider, and so `pnpm dev`, sets it) and `BARRACK_AGENT_USER` unset or naming the supervisor's own user: Pi is spawned with the supervisor's Node, exactly as on a developer's machine, macOS included. The agent can read the supervisor's token through `/proc`; treat it as readable. Without that setting the supervisor refuses to start Pi, saying which variable is wrong and how to fix it, since a missing `BARRACK_AGENT_USER` (a platform that does not pass the image's environment on) or a supervisor started as the agent's user (a user override) would otherwise hand the agent the token silently.
- **Separate user** (the [sandbox image](../../sandbox-image) sets `BARRACK_AGENT_USER=barrack-agent` and runs the supervisor as `barrack-supervisor`): Pi is started as `/opt/barrack/bin/run-as-agent --reuid=<uid> --regid=<gid> --init-groups -- <node> <Pi> <arguments>`. `run-as-agent` is a copy of `setpriv` with the setuid and setgid file capabilities, which only the supervisor's group may run; it changes user and then executes Node in its own place, so Pi has no capabilities. `HOME`, `USER`, `LOGNAME` and `SHELL` are set to the agent user's. The supervisor cannot signal the agent's processes either, so to stop them it runs a short `kill(-1)` as the agent through the same helper, which reaches every process of that user, including commands that started a session of their own.

At startup, before connecting, the supervisor checks a separate user thoroughly and exits with a message naming the problem: an unknown user, a missing or unusable helper, a helper that cannot change user (a sandbox without the `SETUID` and `SETGID` capabilities, or with `no-new-privileges`), and any of the workspace, `pi/agent` and `pi/sessions` that the agent cannot write to. The last check runs a real process as the agent through the helper, so it proves the whole route. The supervisor never creates the agent's directories in this mode; it needs only to pass through them (see the sandbox image's README).

What the agent can and cannot reach as that user is listed in the sandbox image's README.

## The desktop and computer use

The code is in [`src/desktop`](src/desktop) and, for Pi, [`src/pi/computer-use`](src/pi/computer-use); the design is in the [architecture](../../docs/architecture.md#the-live-desktop).

- **Keeping it running.** With `BARRACK_DESKTOP_COMMAND` set, the supervisor starts the command as the agent (through the launcher, like Pi) with only `PATH`, `LANG`, `DISPLAY` and `BARRACK_DESKTOP_VNC_PORT` in its environment, waits until its VNC server greets on loopback, and starts it again, after a pause that doubles up to 30 s, whenever it ends. It tells the control plane after every welcome, and whenever it changes, whether the desktop is `running`, `starting` or `none` (`desktop_availability`). Stopping the supervisor closes the command's standard input, which ends it.
- **Streams.** For each `open_desktop_stream`, the supervisor connects to its VNC server on loopback (and nowhere else, whatever the request says) and dials the stream's URL with its token, then pipes each into the other through Node's stream pipeline, which carries backpressure both ways. At most four are open at once; one it cannot open is answered `desktop_stream_failed`.
- **Control.** At its start, and on every `desktop_control`, it writes `agent` or `user` to `BARRACK_DESKTOP_CONTROL_FILE`, whole and renamed into place.
- **The computer tool.** In a sandbox with a desktop, the Pi harness loads [`computer-use-extension.ts`](src/pi/computer-use/computer-use-extension.ts) (`--extension`) and gives Pi `DISPLAY`, `BARRACK_DESKTOP_VNC_PORT` and `BARRACK_DESKTOP_CONTROL_FILE`. One `computer` tool takes screenshots from the VNC server (one Raw frame, encoded as PNG in the tool), uses the mouse and keyboard through `xdotool`, maps coordinates when the display is larger than a screenshot (1280×800), refuses input while the control file says `user`, and keeps only the newest three screenshots in the model's context. The fake agent's `[desktop]` behaves the same way without Pi, refusing likewise.
- **History.** A tool result's image becomes `[image: image/png]` in what the supervisor reports; screenshots stay in Pi's session in the sandbox.

## Working with a repository

The code is in [`src/workspace`](src/workspace); the whole design is in the [architecture](../../docs/architecture.md#working-with-a-git-repository).

- **Cloning.** After every welcome the control plane sends `prepare_workspace`, which the supervisor carries out before any user message, in the same queue. It clones the repository with `--filter=blob:none` into the workspace, as the agent (through the launcher, like Pi), onto `barrack/<thread id>`, with the user as the commits' author, and records the clone in its state directory, so a resumed sandbox never clones twice. Until the clone succeeds the agent is given no message; each message retries it first.
- **Credentials.** For a repository reached through the GitHub App, the clone's configuration names a credential helper (`git-credential-helper-main.ts`, run by Git as the agent with this Node) and nothing else. The helper asks the supervisor on `BARRACK_GIT_HELPER_SOCKET`; the supervisor answers only questions about the thread's repository, by asking the control plane, and gets a token that can only read that repository for an hour. Nothing is stored or logged; the agent can ask the helper too, which is why the token can only read.
- **Bundles.** When the control plane publishes, the supervisor runs `git bundle create` as the agent, for the work branch's commits since the commit it cloned, into its own state directory within the size and time limits given, and uploads it with its token. Pushing is the control plane's alone.

Git never runs with the supervisor's privileges in the agent's repository, whose configuration and hooks the agent controls, and always with an environment built from an allowlist, never the supervisor's.

## Running it

The control plane starts every supervisor: it creates each thread's sandbox through its [sandbox provider](../../packages/sandbox-providers) with a token minted for that thread alone, which it keeps only as a digest and never reveals. There is no shared token any more, so a supervisor cannot simply be started by hand against a control plane. `pnpm dev` at the repository root runs the control plane with the local-process provider, which starts each thread's supervisor from its sources as an ordinary process; that is the way to run one locally.

**To debug a supervisor**, change how the local-process provider starts it rather than starting it yourself: run the control plane with the variables `pnpm dev` gives it ([`scripts/dev/services.ts`](../../scripts/dev/services.ts)), but with `BARRACK_LOCAL_SUPERVISOR_COMMAND` set to, for example, `["node", "--inspect=0", "/absolute/path/to/apps/sandbox-supervisor/dist/main.js"]`. Paths must be absolute, since each supervisor starts in its sandbox's workspace, and `--inspect=0` gives each one a free port, which Node prints.

**To start one by hand** for a thread that already exists, you need that thread's token, which exists only in the environment of the supervisor the provider started. With the local-process provider that is a process of your own user, so on Linux `tr '\0' '\n' < /proc/<its pid>/environ | grep ^BARRACK_` shows its variables. A supervisor started with the same thread and token replaces it, since the newest supervisor of a thread wins, and the one it replaced exits:

```sh
BARRACK_CONTROL_PLANE_URL=ws://127.0.0.1:8787 \
BARRACK_THREAD_ID=<thread id> \
BARRACK_SUPERVISOR_TOKEN=<that thread's token> \
BARRACK_AGENT_HARNESS=fake \
node apps/sandbox-supervisor/dist/main.js
```

Build it first (`pnpm build`). Add `BARRACK_SUPERVISOR_STATE_DIRECTORY` (any directory of your own) as well. For Pi instead of the fake agent, set `BARRACK_WORKSPACE_DIRECTORY` and `BARRACK_STATE_DIRECTORY` as in the table above; the model and its key come from the control plane once the supervisor is welcomed. Run this way, Pi runs as your own user and can read the token, as with any supervisor and agent that share a user, so also set `BARRACK_AGENT_SHARES_SUPERVISOR_USER=development-only`.

The fake agent quotes each message back word by word. A message containing `[tool]` makes it call a tool first; one containing `[fail]` makes it fail as if its process had crashed; `[model]` makes it name the thread's model; `[quota]` makes it fail as a provider out of quota would. Given a model and no key, it answers that a key is needed, as Pi's harness does. `pnpm --filter @barrack/sandbox-supervisor exec pi --list-models <search>` lists the model identifiers Pi knows.

## How it behaves

- **Pi** runs as a child process in RPC mode, driven by our own JSONL client ([`src/pi`](src/pi)). Readiness is the answer to `get_state`. User messages are sent one at a time as `prompt` with `streamingBehavior: "steer"`, so a busy agent takes them up after its current turn. A message Pi refuses is reported as an errored assistant message. An interrupt is `clear_queue` then `abort`, and drops messages not yet sent. Starting Pi, sending a message, interrupting and stopping take turns in one queue, so a message sent right after an interrupt reaches Pi only once `abort` has been answered and starts a run of its own.
- **Translation** ([`src/pi/pi-event-translator.ts`](src/pi/pi-event-translator.ts)) is pure. A run starts at the first `agent_start` after idle and settles only on Pi's `agent_settled`. User and tool result messages are not forwarded. An assistant message that ended in a model provider error is held back until Pi shows whether it will retry the request (`agent_end.willRetry`, or `compaction_end.willRetry` after a context overflow): it is dropped when the retry starts and recorded as soon as anything else happens, so a failure Pi recovers from shows no error and one it cannot shows exactly one. Tool output over 64 Ki characters keeps its first quarter and last three quarters, where errors and summaries appear.
- **Crashes**: if Pi exits unexpectedly the supervisor sends `agent_failed`, which also ends any run in progress, and starts Pi again on the next user message, reopening the same session file so the conversation continues.
- **A sandbox stopped and started again**: the supervisor starts as a new process, and Pi is started with the thread's identifier as its session identifier in the state directory, which reopens the session it wrote before the stop, so the model is sent the earlier turns (the Docker test `docker-thread-lifecycle.test.ts` checks it). The control plane interrupts the agent before it stops a sandbox, and hands the supervisor no messages while it stops.
- **Stopping**: on `SIGINT` or `SIGTERM` the supervisor closes Pi's stdin (a signal would cut off Pi's last events), waits, escalates to signals if needed, then closes the socket. Pi writes nothing more once its input closes, so a run in progress is reported as settled and interrupted: every run the control plane hears start, it hears end. Every wait is bounded ([`src/pi/pi-stop-timing.ts`](src/pi/pi-stop-timing.ts)): a stop waits at most 3 s for the command Pi is busy with (an interrupt waits for Pi to answer `abort`, which a hung Pi never does), then gives Pi 5 s after its input closes, then sends SIGTERM and after 3 s SIGKILL to the agent's process and every process it started, and gives up waiting 2 s later. That is 13 s at worst, inside the 15 s a Docker sandbox allows. As the supervisor's own user, those signals go to Pi and its descendants as `ps` lists them, which misses a command that left the tree; as a separate user they go to every process of that user.
- **Connection**: reconnects with capped, jittered exponential backoff (up to about 15 s). It exits without reconnecting when the control plane refuses the upgrade with a 4xx status that retrying cannot change (every one but `408` and `429`: wrong credentials, an unsupported protocol version, an unknown endpoint), giving the control plane's reason, or closes with `supersededByNewerSupervisor`; `5xx` answers and network errors are retried. Its own pings detect a dead connection.
- **Acknowledged delivery** (the handshake is in [`packages/protocol/src/supervisor-messages.ts`](../../packages/protocol/src/supervisor-messages.ts)): every connection opens with a hello naming this process (a fresh identifier each start) and how far the agent has been handed user messages. Agent events are numbered and kept in memory ([`src/control-plane/unconfirmed-agent-events.ts`](src/control-plane/unconfirmed-agent-events.ts)) until the control plane confirms them recorded, and everything unconfirmed is sent again after each welcome; stream fragments are sent only on a welcomed connection and otherwise dropped. A user message's sequence is written to `BARRACK_SUPERVISOR_STATE_DIRECTORY` ([`src/delivery/delivered-user-messages.ts`](src/delivery/delivered-user-messages.ts)) before the agent is handed it, so a redelivery, even after a restart, is acknowledged but not handed over again. Stopping waits up to 5 s for the last events to be confirmed.
- **What a supervisor restart loses**: the delivery position survives it; unconfirmed agent events do not (normally milliseconds' worth, or everything since a control plane outage began), and the control plane then closes the run this process left open, saying work was lost. A message noted but not yet handed over when the process dies is lost rather than repeated. If more than 32 Mi characters of events wait unconfirmed, the supervisor exits with an error rather than drop one or keep growing.
- **Size**: every frame must fit the protocol's `maximumAgentEventFrameLength`: `maximumFrameLength` less `threadEventEnvelopeAllowance` (1 KiB) for the envelope the control plane adds when it forwards an event to viewers ([`src/fit-agent-event-in-frame.ts`](src/fit-agent-event-in-frame.ts)). The control plane refuses to record an event whose frame to viewers would not fit, and disconnects the supervisor that sent it. An assistant message too large for that has the middle cut out of each text block, and tool call arguments too large replaced by a note saying how large they were; if that is still too large, its content becomes a notice that it was left out. A stream fragment too large is dropped and logged, since the completed message is the record.
- **Logs**: one JSON object per line on stdout ([pino](https://getpino.io)), each tagged with the thread.

## Tests

`pnpm test` from the root runs them all. The Pi integration test ([`src/pi/pi-agent-harness.integration.test.ts`](src/pi/pi-agent-harness.integration.test.ts)) runs the pinned Pi against a mock model server on `127.0.0.1`, with no network and no real key: it checks which key each request presented, that a replaced key is used without a restart, that a switched model is sent the conversation, and how a rejected key, an exhausted quota and a rate limit are reported. The mock is shared with the end-to-end tests as the workspace package [`@barrack/mock-model-server`](../../tests/mock-model-server). Stopping a Pi that answers nothing is tested with a stand-in ([`src/test-support/unresponsive-pi.mjs`](src/test-support/unresponsive-pi.mjs)).

The separate-user launcher's signalling is not tested here: it signals every process of the user it runs as, which in a unit test would be the test runner's own. `pnpm test:docker` covers it, and everything else about the separate user, with the real image and the real Pi ([`tests/end-to-end/src/docker-agent-isolation.test.ts`](../../tests/end-to-end/src/docker-agent-isolation.test.ts)).
